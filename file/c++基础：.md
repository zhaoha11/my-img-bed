### 1.继承的关键特性：

2.*构造 / 析构顺序*：构造先基类再子类，析构先子类再基类

问题：菱形继承-> 最终子类间接继承同一基类多份副本，导致二义性。

```c++

class B : virtual public A { ... };
class C : virtual public A { ... };
class D : public B, public C { ... }; // D 中只有一份 A 的成员
```

解决：**虚继承**，确保最终子类仅保留一份基类成员。

### 3.什么是C++虚函数？它的实现原理是什么？

​          虚函数是C++实现运行时多态的机制。基类把函数声明为`virtual`后，通过基类指针或引用调用该函数时，实际执行哪个版本取决于对象的动态类型。主流实现中，对象里有虚表指针，虚表里保存虚函数地址，调用时通过虚表查找对应槽位并间接跳转到派生类实现
​        父类指针在编译期决定了你“能调用哪些虚函数”；而子类对象内部的虚指针，在运行期决定了你“具体调用到哪一个类的虚函数”，**即使是static_cast<>向上转型，不改变对象本身**。

### 4.虚函数表中函数指针是如何排布的？基类和派生类的虚表一样吗？

​     在单继承下，基类虚表按照虚函数声明顺序放函数指针。不一样，派生类如果重写某个虚函数，就在相同槽位放派生类函数地址；如果新增虚函数，则在后面追加槽位。因此基类对象和派生类对象不是共用同一张虚表，但派生类虚表的基类部分布局与基类兼容。

### 5.虚析构函数解决什么问题？有虚函数的类 有什么特点？

它解决了当使用“基类指针”去删除“派生类对象”时，派生类析构函数没有被调用，从而导致内存泄漏的问题。

 有虚函数的类有什么特点？

1. 拥有“动态多态”的能力
   这是最直观的特点。通过基类的指针或引用调用虚函数时，程序在运行期才会根据指针实际指向的对象类型，决定去执行哪个类的代码。

2. 内存布局发生变化（增加了 vptr）

   只要类里面有虚函数，编译器就会在这个类的实例对象内部，悄悄插入一个隐藏的指针——**虚表指针（vptr）**。

   - **空间开销：** 这意味着这个类的**每一个实例化对象**，体积都会变大（在 32 位系统上增加 4 字节，在 64 位系统上增加 8 字节）。如果你创建了 100 万个这个类的对
     象，就会多占用几兆的内存。

   3. 产生虚函数表（vtable）

除了对象内部多了一个指针，编译器还会为这个**类本身**在全局只读数据段中生成一张**虚函数表（vtable）**。

- 这张表其实就是一个函数指针数组，里面记录了该类所有虚函数的实际内存地址。
- 对象里的 `vptr` 指针，就指向这张类的 `vtable`。

## 常量指针和指针常量区别：

## 1. 常量指针 (Pointer to Constant)

**定义：** 指向常量的指针。 **形式：** `const int* p` 或 `int const* p`（`const` 在 `*` 的**左边**）。

- **它的含义：** 指针指向的内容是“常量”，不能通过这个指针去修改它指向的数据。

- **它的灵活性：** 指针本身不是常量，它可以随时指向别的变量。

- **生活比喻：** 你是一个房客（指针），你租的房间里的装修（数据）是固定的，你**不能拆墙**。但你租约到期后，可以**搬到另一个房间**去住。

  ## 指针常量 (Constant Pointer)

  **定义：** 指针本身是常量。 **形式：** `int* const p`（`const` 在 `*` 的**右边**）。

  - **它的含义：** 指针存储的地址是固定的，一旦初始化，就不能再指向其他地方。

  - **它的灵活性：** 指向的数据不是常量，你可以通过这个指针修改它指向的内容。

  - **生活比喻：** 你买了一套房，这辈子只能住这（**地址固定**），但你想把房里装修成什么样都行（**内容可变**）。

    在 C++ 中，`static` 和 `inline` 是两个使用频率极高、但作用维度完全不同的关键字。一个主要关乎**生命周期与可见性**，另一个主要关乎**编译优化与定义规则**。



## ++a和a++

- **前置 `++a`（先加后用）**：
  在内置类型中，`++a` 的结果就是“自增后的 `a` 本身”。因为返回的就是对象本身，所以它自然是一个**左值（L-value）**。既然是左值，返回 `T&`（引用）是最完美的，既符合语义，又避免了拷贝。

- **后置 `a++`（先用后加）**：
  在内置类型中，`a++` 表达式的结果必须是**“自增之前的旧值”**。既然旧值已经被 `a` 覆盖了，为了把这个旧值传出去，编译器（或重载函数）必须在内存中创建一个**新的临时对象**来保存它。这个临时对象在表达式结束后就会销毁，因此它只能是一个**纯右值（PR-value）**。既然是右值，就绝对不能返回引用（返回局部变量的引用会导致悬空指针/野指针）。

**`new` 然后 `free` 释放：发生资源泄漏** 当你使用 `new` 创建一个对象时，C++ 不仅分配了内存，还**调用了构造函数**。如果这个对象内部包含了其他动态分配的资源（例如 `std::string`、打开的文件句柄、网络连接等）。 当你用 `free` 释放它时，`free` 只会机械地把对象占用的这块“外壳”内存还给操作系统，**它不会调用析构函数**。结果就是，对象内部申请的那些资源永远丢失了，造成严重的内存泄漏或资源枯竭。

## 4.完美转发（参数转发机制）

**左值（Lvalue）：** 指的是在内存中有确定存储地址、有变量名的数据。通俗来说，能放在等号左边、能取地址（`&`）的就是左值。

**右值（Rvalue）：** 指的是即将被销毁的、没有名字的临时变量（例如函数返回的临时对象、字面量 `10`）。它们通常只能放在等号右边，无法取地址。****



核心应用一：移动语义

 核心应用二：完美转发

完美转发 = 保持参数原本的值类型（左值 / 右值）不变，原封不动转发给下一个函数。不丢失类型信息，不产生多余拷贝，最大化利**用移动语义**提升性能

使用场景：

必须是**模板加参数&&**，

```c+
template<typename _FUNCTION_, typename...ARGS>
class CFunction :public CFunctionBase
{
    std::function<int()>m_binder;// 统一的“可调用对象”包装
public:
    CFunction(_FUNCTION_&& func, ARGS&&... args) {
        m_binder = std::bind< int>(
            std::forward<_FUNCTION_>(func),
            std::forward<ARGS>(args)...
        );
    }
    ~CFunction() override = default;
    virtual int operator()() override {
        return m_binder(); // 调用已绑定的函数
    }
};
```

**构造函数使用万能引用（模板 +&&）**

可以接收任意类型的函数对象（左值 / 右值）、任意类型、任意个数的参数。

**使用 std::forward 转发**

将函数和参数**原封不动**转发给 `std::bind`，保持：

- 左值 → 转发为左值

- 右值 → 转发为右值

  不会产生额外拷贝，保留移动语义，效率最高。

## 8.share_ptr底层实现

核心思想：共享所有权和引用技术

当你写下 `std::shared_ptr<int> p(new int(10));` 时，`p` 这个对象本身（通常分配在栈上）其实占用了两个指针的大小（在 64 位系统上是 16 字节）。

它包含：

1. **数据指针 （线程不安全）**：直接指向你实际申请的那个对象（也就是堆上的那个 `10`）。
2. **控制块指针 **：指向堆上的另一个神秘区域——**控制块 **。

控制块：（线程安全）实现共享和自动释放，里面有

强引用计数：为0，删除数据对象

弱引用计数：为0，删除控制块

自定义删除器 ：

分配器 ：

`unique_ptr` 的底层实现并不复杂，它本质上是一个**零开销抽象**的模板类。它的核心逻辑在于：**持有裸指针，并利用RAII机制在析构时自动释放资源；同时通过禁用拷贝构造函数、启用移动语义来保证资源的独占所有权**，不能私有化，要禁用

```c++
template<typename T, typename Deleter = std::default_delete<T>>
class unique_ptr {
private:
    // 核心数据成员：通常是一个 tuple 或两个成员变量
    T* ptr;        // 1. 原始指针，指向管理的资源
    Deleter del;   // 2. 删除器对象，用于释放资源,不占用内存
public:
    // ... 核心操作
};
```

shared_ptr循环引用如何产生：

**循环引用**就是：两个 / 多个对象互相持有对方的 `shared_ptr`，导致**引用计数永远无法降到 0**，内存永久无法释放，造成**内存泄漏**。

`shared_ptr` 通过引用计数管理内存：每增加一个 `shared_ptr` 指向同一对象，引用计数 +1；`shared_ptr` 销毁时引用计数 -1，当计数为 0 时自动释放对象。

**循环引用**发生在对象之间通过 `shared_ptr` 相互持有，形成闭环。



**智能指针本质：RAII 资源获取即初始化**

## auto的类型推导原理：

**本质**：模板参数推导

 三大核心推导规则：

根据是否给auto加了引用&或指针*修饰符

**情况 A：**按值推导 (`auto x = expr;`)

x是一个全新的副本，expr身上的“引用属性”和“顶层常量属性（top-level const）”都会被**抛弃（Decay/退化）**。此外，数组和函数名会退化为指针。

#### 情况 B：按引用或指针推导 (`auto& x = expr;` 或 `auto* x = expr;`)

当你加上 `&` 或 `*` 时，你告诉编译器：“我不想发生拷贝，我要直接指向或引用那个东西”。

- **规则：** 此时，表达式的“常量属性（constness）”会**被严格保留下来**，但引用属性会被忽略（因为你已经显式写了 `&`）。

#### 情况 C：万能引用推导 (`auto&& x = expr;`)

这是现代 C++ 中非常强大的特性，通常用于泛型编程和完美转发。

- **规则：** 编译器会根据等号右边的表达式是“左值”（有内存地址的变量）还是“右值”（临时的、即将销毁的值）来做决定。它使用了引用折叠（Reference Collapsing）规则。
  - 如果 `expr` 是左值，`auto&&` 会推导为**左值引用 (`Type&`)**。
  - 如果 `expr` 是右值，`auto&&` 会推导为**右值引用 (`Type&&`)**。

### decltype关键字：


## 右值引用：

### 左值引用 `T&` 的局限

可以绑定到左值，`const T&` 甚至可以绑定到右值，但这有个致命问题：**它无法区分“这个对象是永久存在的”还是“马上要销毁的”。**

所以不能做返回值为引用，可能会空引用，

传统左值引用可以避免复制传参，但是避免不了返回值的深拷贝，移动构造`temp` 内部的动态数组、字符串指针直接**转移**给外面的临时对象

`const T&` 提供兼容性，`T&&` 提供移动语义的性能优化。

右值引用和左值引用的区别

| :---------------------------- | :------------------------ | :------------------------------- | :--------------------------------- |
| **`const T&` (常量左值引用)** | 万能引用，可绑定左值/右值 | 任何对象                         | “我只读，不关心你是否即将销毁”     |

`const T&` 是万能引用，**左值、右值全都能绑**。

## 什么是原子变量，原子操作：

**概念： 原子操作是对共享变量的一次不可分割访问，能够避免多个线程同时读写造成数据竞争。C++里可以用`std::atomic<T>`，常见操作包括`load`、`store`、`fetch_add`和`compare_exchange`。底层通常依赖CPU原子指令和C++内存模型，不只是“加锁的替代品”，还需要关注内存可见性和操作顺序。**

为什么需要原子操作：

原子操作保护cpu读-改-写这三个步骤为一个执行整体，避免被其他

######原子变量自带屏障atomic x.load(memory_order __m = memory_order_seq_cst),这在底层会插入昂贵但绝对安全的内存屏障，保证所有线程看到所有原子变量的修改顺序都完全一致。

**如果没有明确指定`release`和`acquire`，编译器会使用默认的最强屏障`seq_cst`，结果系统性能通常会变得更慢。**

为了实现这种极其严苛的全局一致性，系统必须付出高昂的性能代价：

1. **全功能内存屏障（Full Memory Barrier）：** 在 x86 架构下，编译器通常会为 `seq_cst` 的写操作生成带有 `LOCK` 前缀的指令（如 `XCHG`）或显式的 `MFENCE` 指令。这种指令充当了全功能内存屏障。
2. **清空写缓冲区（Store Buffer Flushing）：** 该屏障会强制当前 CPU 核心将写缓冲区（Store Buffer）中的所有挂起操作立即刷新至 L1 缓存或主存。
3. **总线锁定与缓存一致性开销（Bus Locking & Cache Coherency）：** 为了确保全局全序，CPU 必须通过缓存一致性协议（如 MESI 协议）向其他所有核心广播失效信号（Invalidate Message），并**阻塞等待**所有核心的确认响应（Acknowledge）。这种跨核心的同步通信会导致严重的指令流水线停顿（Pipeline Stall），极大地增加了访存延迟。





## C++ 内存序与内存屏障底层原理

一、 硬件根源：CPU 为什么要“乱序”？
  为了提升 CPU 吞吐量，现代 CPU 引入了多级缓存（L1/L2/L3）和 **MESI 缓存一致性协议**。但 MESI 协议在跨核通信时存在**同步等待延时**，硬件工程师为了挤干 CPU 性能，引入了两个异步缓冲区：

1. Store Buffer（存储缓冲区）

- **引入原因**：CPU 0 写数据时需要向其他核心广播 `Invalidate` 消息并**等待确认**，为了不让 CPU 闲置，写操作先塞进 Store Buffer，CPU 接着干别的事。
- **副作用（Store-Load 乱序 / 写后读乱序）**：写操作还在 Store Buffer 里没真正刷入缓存，后续的读操作已经执行了，导致其他核心看到“写先于读，但实际读拿到了旧值”。

### 2. Invalidate Queue（失效队列）

- **引入原因**：Store Buffer 容量极小，如果其他核心响应 ACK 太慢， Store Buffer 满了 CPU 依然会卡死。因此接收端引入 Invalidate Queue，收到失效消息**不立即清理 L1，而是先放队列并“瞬间假回复 ACK”**。
- **副作用（Load-Load 乱序 / 读后读乱序）**：CPU 读数据时，相关的失效消息还躺在 Invalidate Queue 里没来得及处理，导致 CPU 直接从自己的 L1 缓存里读到了**脏数据/旧数据**。

**硬件层总结**：为了加速，CPU 将 MESI 协议的同步动作推迟了，**Store Buffer 导致了写乱序，Invalidate Queue 导致了读乱序**，所以这里的乱序”不一定意味着 CPU 真的把汇编指令位置交换了，很多时候指的是**内存操作对其他线程的可观察顺序与程序顺序不同**。

二.  内存屏障就是硬件暴露给程序员的指令，用来强制清空缓冲区，恢复顺序：
1.写屏障（Store Barrier / Write Barrier）
  **作用**：强制把 Store Buffer 中的数据刷入 L1 缓存，或标记后续写操作必须等待 Store Buffer 清空。
  **解决**： Store-Store / Store-Load 乱序，保证**写操作的可见性**
2.读屏障（Load Barrier / Read Barrier）
  **作用**：强制处理完 Invalidate Queue 中的所有失效消息，使本地 L1 缓存失效。
  **解决**： Load-Load 乱序，保证**能读到最新的写**。
3.**全屏障（Full Barrier）**
  **作用**：同时清空 Store Buffer 和 Invalidate Queue，CPU 彻底停顿等待，保证**全局顺序一致性**。

三,从屏障到内存序：C++11 提供了统一的抽象：**用内存序控制编译器重排 + 自动插入底层硬件屏障**。

| **C++ 内存序**     | **约束语义**                                                 | **硬件/屏障层面做了什么**                               | **典型应用场景**                             |      |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------- | -------------------------------------------- | ---- |
| **`relaxed`**      | 仅保证当前变量自身修改的**原子性**，不提供任何跨线程的同步与重排限制。 | 不插入任何内存屏障指令，允许编译器/CPU 自由重排。       | 纯计数器（`fetch_add`）、引用计数增加。      |      |
| **`release` (写)** | 本线程中**在此之前的任何读写**，绝不能被重排到此 Release 操作之后。 | 刷清 **Store Buffer**（插入写屏障），确保数据已落地。   | 生产者发布数据、单例模式赋值。               |      |
| **`acquire` (读)** | 本线程中**在此之后的任何读写**，绝不能被重排到此 Acquire 操作之前。 | 清空 **Invalidate Queue**（插入读屏障），确保读到最新。 | 消费者读取标志位、单例模式检查。             |      |
| seq_cst            | 最强约束，所有线程看到的所有 `seq_cst` 操作有一个**全局唯一的绝对顺序**。 | 强制插入**全屏障**，清空所有缓冲区并停顿等待 ACK。      | 默认选择、状态机切换等对全局顺序敏感的场景。 |      |



总结：
**编译器重排**：处理的是未定义行为（数据竞争），需要用 C++ 语言规范（如原子变量）明确告诉编译器规避。
**硬件乱序**：起源于 **Store Buffer (写乱序)** 和 **Invalidate Queue (读乱序)** 的引入。
**内存屏障**：是 CPU 提供的硬件指令，用来手动清空上述缓冲区。
**C++ 内存序**：是语言给程序员提供的控制工具，**把程序员从手动写硬件屏障的泥潭中解放出来**，兼顾了高性能与跨平台跨架构（x86/ARM）的一致性。

​     在发生写屏障时，之前写的操作由store buffer中都清空，然后通知其他核心队列该变量发生改变，但是不会立刻改变，而是放入失效队列，并回复ACK，然后在读内存序时清空，告知以更改，所以两个操作缺一不可

## 静态类型和动态类型

在c++种，一个指针有静态类型和动态类型

**静态类型：** 编译时（写代码时）就确定类型。

**动态类型：** 运行时（程序跑起来时）才确定类型。

动态类型则是指**一个指针或引用，在“运行期”实际所指向或引用的对象的类型**。

- **特点：** 它只有在**运行期**才能最终确定，并且**可以随着指针指向的改变而改变**。
- **核心前提：** 在 C++ 中，**只有基类的指针或引用，并且关联了虚函数（Virtual Function）时**，讨论动态类型才有实质性的意义。

静态类型：static_cast是一个编译期行为，只能改对象静态类型，没有改对象数据
如果static_cast<>强行改了动态类型会产生什么问题：
1.多态消失
2.对象切片，指针转型不会发生切片，但**值传递**会发生切片

dynamic_cast：
条件：基类必须至少包含一个**虚函数**，`dynamic_cast` 的安全检查极度依赖 **RTTI（运行时类型信息）**，而 RTTI 存在于虚函数表中。
向下转型时，会确定这个对象指向的时基类还是派生类，根据<>类型确定赋值是个否位nullptr,

```
Base* b_real_base = new Base(); // 它的真身就是个父类
Derived* d1 = static_cast<Derived*>(b_real_base); 
d1->childFunc(); // 噩梦开始！
//严格审查
Derived* d2 = dynamic_cast<Derived*>(b_real_base);


```

| 特性     | 向上转型 Upcasting            | 向下转型 Downcasting             |
| -------- | ----------------------------- | -------------------------------- |
| 转换方向 | 派生 → 基类                   | 基类 → 派生                      |
| 隐式转换 | public 继承下支持自动隐式转换 | 不支持，必须强制转换             |
| 安全性   | 绝对安全                      | 不安全，极易内存越界             |
| 多态     | 依靠向上转型实现多态          | 需要转型后才能访问派生独有成员   |
| 推荐用法 | 直接赋值                      | 优先 `dynamic_cast` + 判断空指针 |

`dynamic_cast`：继承体系安全向下转型，带运行时检查，需要虚函数 + RTTI

## 动静态库

静态库在链接时把所需代码合入可执行文件；动态库在链接时只记录依赖关系和符号信息，程序启动时由动态链接器把共享库映射到进程地址空间，或者运行时通过`dlopen`加载。调用动态库函数时，再通过动态链接机制解析到真实地址。

动态库调用慢在哪里？动态库函数调用通常多一次间接寻址，首次调用还可能触发符号解析。Linux ELF体系中常用PLT/GOT实现延迟绑定：第一次调用时通过PLT进入动态链接器解析符号，并把真实地址写入GOT；后续调用直接从GOT取地址跳转。这样把昂贵的查找过程缓存起来，避免每次调用都解析符号。

**PLT**：**Procedure Linkage Table**，过程链接表

**GOT**：**Global Offset Table**，全局偏移表

动态链接库（.so/.dll）在多进程运行时，其代码段在物理内存中只有一份吗？如果是，不同进程的全局变量和静态变量又是怎么隔离的？

1.代码段在物理内存中**只有一份**。通过操作系统的虚拟内存映射和页表，多个进程共享这块物理内存。

2.**数据隔离**：动态库利用 **PIC（位置无关代码）** 技术和 **GOT（全局偏移表）**。每个进程在自己的数据段（Data Segment）中拥有该动态库全局变量的独立副本。当进程尝试修改共享的数据页时，操作系统会触发 **COW（写时复制，Copy-on-Write）** 机制，确保进程间互不影响。

怎么设计动态库？

```c++

#pragma once

#ifdef _WIN32
//当前正在编译这个工程，最终产物是动态库（dll/so），请把标记了 MYLIB_API 的接口暴露出去，写入库的导出符号表。

    #else

        #define MYLIB_API __declspec(dllimport)

    #endif
```

| ----------------------- | -------------------- | ------------------------------------------------- |
| `__declspec(dllexport)` | **编译 DLL 库本身**  | 把函数写入 DLL 导出表，生成`.lib`导入库，给别人用 |

### **1. 接口隔离：面向接口与隐藏实现**

- **纯虚基类（Interface）**：对外仅暴露包含纯虚函数的基类，将具体实现类完全隐藏在动态库内部。调用方通过基类指针以多态方式调用，彻底解耦高层逻辑与底层实现。
- **Pimpl 惯用法（不透明指针）**：如果必须传递对象，使用不透明指针（Opaque Pointer）将类的成员变量隐藏在内部，避免头文件依赖并增强二进制兼容性。
- **C 风格工厂函数**：对外暴露的创建和销毁接口必须使用 `extern "C"` 声明，禁用 C++ 的名称修饰（Name Mangling），确保符号能被外部程序（甚至其他语言）稳定解析。

### **2. 内存安全：谁分配，谁释放**

- **严禁跨模块内存操作**：主程序和动态库可能拥有不同的内存堆（Heap）或运行时库（CRT）。绝不能在动态库中 `new`，而在主程序中 `delete`，这会直接导致堆破坏和程序崩溃。
- **提供配对的生命周期 API**：动态库必须提供成对的 C 风格创建和销毁函数（如 `create_xxx` 和 `destroy_xxx`），确保内存始终在同一个模块的堆中分配和释放。
- **禁止跨边界传递复杂对象**：绝不跨越 DLL/SO 边界传递 `std::string`、`std::vector` 等 STL 容器，应使用 POD（Plain Old Data）结构或 C 风格字符串（`const char*`）。

## vector:

介绍
 `vector`的特点要从“连续内存 + 随机访问 + 尾插高效 + 中间插删代价高 + 扩容导致失效”几个核心点来回答，而不只是背三个指针。

`vector`最核心的特点是底层连续内存，因此支持O(1)随机访问，缓存局部性也比较好。它适合尾部插入、顺序遍历和需要与底层数组兼容的场景。缺点是中间插入删除会搬移元素，扩容时还可能整体迁移内存，所以扩容后原有迭代器、指针和引用通常会失效。实现上通常会维护起始、已用末尾和容量末尾这几个指针或等价信息。
扩容：
`vector`扩容时会先申请一块更大的原始内存，然后把旧内存中的元素逐个搬到新内存中，这一步可能通过拷贝构造，也可能通过移动构造完成。等新内存中的对象都构造好之后，再析构旧内存里的对象，释放旧缓冲区，最后更新`begin/end/capacity`这些内部状态。整个过程本质上是对象级迁移，不是简单的字节复制。扩容后`size`不变、`capacity`增大。

能不能直接memcpy把旧内存拷到新内存？

一般不能。因为`vector`存放的是对象，不是单纯的字节块。扩容时需要正确地在新内存上构造对象，并在旧内存上析构对象。如果直接`memcpy`，对于含堆资源、智能指针、文件句柄、虚函数等非平凡类型，只会得到一份字节级浅拷贝，破坏对象语义，可能导致双重释放、悬空指针或未定义行为。只有在`T`是trivially copyable时，字节复制才可能成立，但通用`vector`实现不能默认这么做。

为什么要重新申请新内存？
因为动态数组要求底层内存连续，而原缓冲区后面的地址空间不一定还空着，可能已经分配给别的对象了。只要无法保证“原地后续空间也连续可用”，就不能直接往后长。所以通用做法只能是重新申请一块更大的连续内存，把旧元素搬过去，再释放原来的空间。

## 哈希表的设计

\1. 哈希函数：要设计均匀的哈希算法，避免大量 key 映射到同一个 bucket，导致链表过长。
\2. 扩容机制：当负载因子超过阈值（通常 0.75）时触发扩容。为了避免一次性 rehash 卡顿，可以采用渐进式 rehash，分批迁移数据。
\3. 冲突解决：链地址法处理冲突，当链表长度超过阈值（如 8）时转为红黑树，查询复杂度从 O(n) 优化到 O(log n)。
\4. 多线程安全：可以采用分段锁，每个 bucket 一把锁，不同线程操作不同 segment 时可以并发执行，相比全局锁大幅提升并发性能
\5. 有序性：哈希表无序，如果需要范围查询，应该用有序结构如红黑树实现的 map。

## 线程和进程的主要区别是什么

## 进程内存的全局布景

在32位操作系统，一个进程通常有4GB的虚拟内存空间，分为用户空间和内核空间
**用户空间：**

**代码段（Text Segment）：** 存放编译后的二进制机器指令。
**初始化数据（Data Segment）：** 存放已初始化的全局变量和静态变量。
**未初始化数据（BSS）：** 存放未初始化的全局变量和静态变量（自动初始化为 0）。
**堆（Heap）：** 动态内存分配区域（C++ 中用 `new`/`malloc` 申请的空间）。**向高地址增长**。
**内存映射区 / 自由区** ：

1. **动态链接库：** 进程加载的 `.so` 共享库（如 `libc.so`, `libpthread.so`）。 
2. 子线程的独立栈（Thread Stacks）：当你调用 `pthread_create` 时，系统会在这里调用 `mmap` 分配一块连续空间（默认通常是 8MB），作为**新线程的独立栈**
3. **线程控制块 (TCB / `struct pthread`)：** 每个子线程栈的底部或顶部，紧挨着一块用来存放该线程核心档案（线程状态、退出码、用户态寄存器镜像）的结构体。**你手里的 `pthread_t` 数组里存的数值，本质上就是这个 TCB 的内存起始地址**。
4. **进程间共享内存：** 通过 `shmget` 或 `mmap` 显式申请的 IPC 共享内存也在这

**栈（Stack）：** 存放局部变量、函数参数、返回地址等。**向低地址增长。**

内核空间（Kernel Space）

内核空间是所有进程共享的，用户程序**不能直接访问**它。

里面存放的是操作系统的内核代码、内核数据结构（如进程表、页表）、内核栈，以及驱动程序等。

只有当你的程序执行**系统调用**（比如系统 I/O、网络收发 `send`/`recv`）或者发生硬件中断时，CPU 才会切换到特权模式（Kernel Mode），进入内核空间执行代码。





## 2.进程控制块 PCB（核心）：

1.**PCB 是什么**

- 操作系统管理进程的**唯一数据结构**
- 是进程存在的**唯一标志**

2.**PCB 包含内容**

- 进程标识信息（PID、父进程 ID）

- **文件和 I/O 状态：** 记录这个进程打开了哪些文件（文件描述符表）、使用了哪些网络 Socket、有哪些正在进行的 I/O 请求。

  处理机状态信息（寄存器、程序计数器 PC）

- 进程调度信息（状态、优先级、等待时间）

- 进程控制信息（资源清单、指针）

3. **操作系统是怎么通过 PCB 管理进程的？**

**当进程准备好运行了：** 它的 PCB 就会被挂到“就绪队列”里排队。

**当进程在等网络数据（比如你的 Socket 等待接收 `recv`）：** 它的 PCB 就会被从就绪队列取下，挂到“阻塞队列”里。CPU 此时就不会把时间浪费在它身上。

**当网络数据到了：** 硬件产生中断，操作系统把它的 PCB 从阻塞队列移回就绪队列，等待 CPU 调度

### 进程的隔离性：

**1.内存隔离：**

页表映射：操作系统为进程分配独立页表，当进程访问虚拟地址，CPU中的MMU根据专属页表翻译成真正的物理内存地址

物理隔离：

越界保护：访问未经映射的虚拟内存，MMU发送段错误，直接杀掉进程

**2.指令隔离：**CPU的特权级与系统调用

CPU 在硬件层面上划分了特权级（通常称为 Ring 模型，如 x86 的 Ring 0 到 Ring 3）。

进程在权限最低的用户态（Ring 3），必须执行系统调用

**3.执行流隔离：**上下文保护和恢复，会把当前进程的CPU寄存器保存到PCB中，放下一个进程的上下文

**4.资源隔离**：

资源句柄是进程私有的，必须通过内核代理，用户态也无法伪造内核态指针，有权限隔离

### 进程调度

**1. 非抢占式调度**

非抢占式调度是指：一个进程一旦获得 CPU，就会一直运行，直到它主动放弃 CPU

典型算法：

- 先来先服务，FCFS
- 非抢占式短作业优先，SJF

**2. 抢占式调度**

抢占式调度是指操作系统可以在时间片用完、有更高优先级进程到达、发生中断等情况下，强制暂停当前进程，把 CPU 分配给其他进程。常见算法有时间片轮转 RR、优先级调度、最短剩余时间优先 SRTF、多级反馈队列 MLFQ 等。

**时间片轮转 (Round Robin, RR)：** 最公平的算法。每个进程分配一个微小的时间片（如 10ms），用完就去排队。

**优先级调度 (Priority Scheduling)：** 给进程打分。比如系统内核任务优先级高于 UI 渲染，UI 渲染高于后台下载。

**多级反馈队列 (Multi-Level Feedback Queue)：** Windows 等现代系统常用的复杂方案。如果一个进程老是耗满时间片（CPU 密集型），就降低它的优先级；如果它经常因为等待 I/O 而放弃 CPU（I/O 密集型），就提高它的优先级，以保证交互灵敏度。

**完全公平调度 (CFS, Linux 默认)：** 它不看时间片，而是看 `vruntime`（虚拟运行时间）。调度器总是挑选 `vruntime` 最小的进程运行，并使用**红黑树**来高效管理这些进程。

### 信号： 

信号的本质是 **软件中断（Software Interrupt）**。
 **硬件中断**：当鼠标点击、网卡收到数据包时，硬件向 CPU 发出电信号，CPU 暂停当前手头的工作，跳转去执行对应的中断服务程序（ISR）。

**软件中断（信号）**：内核（Kernel）向某个进程发送一个异步通知，告知它某个事件已经发生。进程必须暂停当前的用户空间代码，转去执行对应的信号处理函数（Signal Handler）。

**信号的底层机制：**

内核在每个进程的 `task_struct`（进程控制块）中维护了相关的信号位图（Bitmaps）。主要有两个核心结构：

- **未决信号集（Pending）**：一个位图。如果某一位被置为 1，说明该信号已经产生，但进程还没有来得及处理（处于未决状态）。
- **阻塞信号集（Block / Mask）**：也是一个位图，常称为“信号屏蔽字”。如果某一位被置为 1，表示进程目前拒绝接收该信号。此时如果该信号产生，会一直保持在 Pending 状态，直到进程解除阻塞。

**信号的作用：**
处理系统异常，

通知异步事件：例如，子进程退出时，内核会向父进程发送 `SIGCHLD` 信号，通知父进程去回收子进程的资源，避免产生僵尸进程。

管理员退出：你在终端输入 `Ctrl + C`，其实是向前台进程组发送 `SIGINT`（中断信号）；执行 `kill -9 <PID>`，则是发送 `SIGKILL`（强制杀死信号）。

**信号的递达与处理**

当进程从**内核态返回到用户态**的那个瞬间（例如系统调用结束、或时间片耗尽发生调度时），内核会检查该进程的 Pending 集。

如果发现有信号，且没有被 Block，内核就会让进程去执行相应的**动作（Action）**。进程对信号的处理有三种选择：

1. **执行默认动作（Default）**：系统对每种信号都有默认处理方式（如 Terminate 终止、Core 终止并吐核、Ignore 忽略、Stop 暂停）。
2. **忽略（Ignore）**：对该信号不作任何处理（注意：`SIGKILL` 和 `SIGSTOP` 不能被忽略，也不能被捕捉）。
3. **捕捉（Catch）**：进程提前通过 `signal()` 或 `sigaction()` 系统调用，为某个信号注册一个**自定义的回调函数**。当信号递达时，执行这个函数。

### sockpair相比于普通管道有什么区别

#### 1. 通信方向（全双工 vs 半双工）

- **普通管道：** 当你调用 `pipe(fd)` 时，系统会给你两个文件描述符。水流只能从一端流向另一端。如果你需要父子进程互相说话，你**必须创建两个管道**（一个用于父传子，一个用于子传父），这会消耗 4 个文件描述符。
- **`socketpair`：** 当你调用 `socketpair(..., fd)` 时，返回的两个描述符是相互连接的套接字。向 `fd[0]` 写入的数据可以从 `fd[1]` 读出，向 `fd[1]` 写入的数据可以从 `fd[0]` 读出。**只需要创建一个 `socketpair` 就可以实现父子进程的双向对话。**

#### 2. 传递文件描述符（杀手级特性）

- **普通管道：** 只能用来传输普通的字节（文本、二进制数据）。
- **`socketpair`：** 因为它底层是 Unix 域套接字，所以它可以使用 `sendmsg` 和 `recvmsg` 这两个系统调用来发送/接收**辅助数据（Ancillary data）**。这在多进程架构中极其重要——主进程可以打开一个文件或网络连接，然后通过 `socketpair` 把这个“文件描述符”直接发给工作进程（Worker Process）。像 Nginx、Chrome 浏览器的多进程架构中都大量使用了这个特性。普通管道绝对做不到这一点。

#### 3. 数据类型的灵活性

- **普通管道：** 就是一个纯粹的字节流（Stream），类似于 TCP，没有消息边界。如果你一次写入 "Hello"，另一次写入 "World"，接收端可能一次性读出 "HelloWorld"。
- **`socketpair`：** 创建时可以选择 `type` 参数。
  - 如果选 `SOCK_STREAM`，它的表现和管道一样，是可靠的字节流。
  - 如果选 `SOCK_DGRAM`，它就变成了基于数据报的通信，每次读写都会**保留消息边界**，发几次就要收几次，不会发生“粘包”问题，且在本地通信中依然是可靠的。





## 死锁的四大条件：

**互斥条件（Mutual Exclusion）：** 资源是独占的。一个玩具同一时刻只能被一个小孩拿在手里。

**占有并等待（Hold and Wait）：** 线程已经保持了至少一个资源，但又提出了新的资源请求，而该资源已被其他线程占有。此时请求线程阻塞，但对**自己已经获得的资源保持不放**。

**不可剥夺（No Preemption）：** 线程已获得的资源，在未使用完之前，不能被操作系统强行剥夺，只能由自己主动释放。

**循环等待（Circular Wait）：** 必然存在一个线程和资源的环形链。比如 线程1等线程2，线程2等线程3，线程3等线程1。

解法一：破坏“循环等待” —— 统一加锁顺序 (Lock Ordering)

解法二：破坏“死等” —— 使用超时机制 (Timeout / try_lock)

尝试拿锁 B，如果拿不到，**主动放弃自己已经占有的锁 A**。

退后一步，等待一段随机时间，然后从头再来。

这就像是在狭窄胡同里两车相遇，总得有一辆车先倒车让路，交通才能恢复。

## 悲观锁和乐观锁：

**悲观锁**：悲观预判冲突频发，**先加锁、再操作、最后释锁**，资源被独占，其他线程无法修改，会产生阻塞。

**乐观锁**：乐观预判冲突极少，**不加锁直接操作**，提交时校验数据状态，冲突则放弃 / 重试，无阻塞、并发吞吐更高。

## 内存碎片：

**内存碎片**是指由于频繁的内存分配与释放，内存中出现了大量不连续、无法被有效利用的“缝隙”，导致虽然总空闲内存足够，却无法满足大块连续内存的分配请求，造成浪费甚至程序崩溃。

外部碎片：

**定义**：已分配内存块之间的空闲区域太小且不连续，无法被新的分配请求使用。

内部碎片：

**定义**：分配器给程序的内存块比实际需要的稍大，多余的部分无法被其他请求使用。

解决办法：
os层面：分页+虚拟内存，将不连续的物理页映射成连续的虚拟地址空间
**内存池技术**：提前申请一大块连续内存，内部划分固定大小字节，可以被同等大小请求复用，消除外碎片
**实现方式**：申请大内存，切分成固定大小格子，内部用无锁链表将格子串连，可以通过重载类的 `operator new` 和 `operator delete`，让该类的所有对象自动走内存池分配。

##  TCP三次握手：

第一次握手：客户端发送一个SYN包，序列号为x,给服务器表示要求建立连接，进入SYN_SENT状态，等待服务器响应

第二次握手：服务端收到客户端SYN包之后，发送一个初始序列号为y的SYN-ACK包给客户端，服务器进入SYN-RECEIVED状态，等待客户端确认

第三次握手：客户端接收到SYN-ACK包后，发送ACK包给服务器，带一个ack确认号y+1，表示收到服务器SYN包**双方状态：**客户端和服务器都进入ESTABLISHED状态，连接成功建立，接下来可以进行数据传输。

半连接队列：第二次握手，放入半连接队列，第三次握手收到ACK，校验合法移入全连接队列

全连接队列：调用accept()取走TCP连接,长度有listen(fd,backlog)决定
队列满了,当全连接队列满，此时服务端收到客户端第三次 ACK？
linux丢弃ACK，不会回复RST
客户端处于 `ESTABLISHED`，以为连接成功
客户端发数据会被服务端回 RST，连接直接断开



如果第三次握手的 ACK 丢失，服务端收不到 ACK，连接停留在 SYN_RCVD 状态。服务端有超时重传机制，会重发 SYN+ACK 包，重传次数由内核参数 tcp_synack_retries 控制（默认 5 次），重传间隔指数退避。

客户端已经发送了 ACK，认为自己已经建立连接，处于 ESTABLISHED 状态。如果此时客户端发送数据，服务端会因为没有完成握手而回复 RST。所以实际工程中，应用层通常需要设计心跳或超时重连机制来处理这种不对称状态。

## 四次挥手：

客户端发送Fin包，带上自身序列号，表示请求关闭，进入等待服务器响应状态

服务器收到Fin包后，发送ACK包，表示收到请求，进入关闭等待状态，可能还有数据要发，客户端进入等待服务器关闭请求

服务器发送Fin包，，带上自身序列号，表示服务器准备关闭，服务器等待客户端确认

客户端收到Fin包后，发送ACK包给服务器，确认关闭，客户端进入**TIME-WAIT状态，等待2MSL（**最大报文生存时间）后关闭连接，确保连接彻底断开

**服务器状态：**服务器收到ACK包后，进入CLOSED状态，连接断开

2MSL的原因：给 ACK 丢包留一次补救机会，清理网络残留报文。

## TCP的拥塞控制机制：

拥塞窗口cwnd,决定把多少数据推向网卡

阈值(ssthresh)：也叫慢启动阈值（通常65535个字节）

核心机制（四个阶段）：

**慢启动：**刚开始发送时，cwnd为1个MSS(最大报文段)，每收到一个ACK，cwnd就加1，宏观上看，每经过一个往返时间（RTT），窗口大小**呈指数级翻倍**（1 → 2 → 4 → 8）。虽然叫“慢”启动，但增长速度极快，目的是迅速探明网络的可用带宽。

**拥塞避免**：当cwnd增长到达阈值ssthresh时，为了避免压垮网路，增长方式由指数变为线性增长，每经过一个RTT，cwnd加1

拥塞发生（超时 / 丢包）：

   如果是严重拥塞：ACK都不回来，阈值降为cwnd的一半，cwnd暴跌回1，重新进入慢启动
  如果是轻微拥塞（收到3个重复ACK）：说明中间包丢了，内核触发快重传，将 `ssthresh` 降为cwnd一半，并且 `cwnd` 也降到新的 `ssthresh` 附近，直接进入线性的拥塞避免阶段，而不是跌回 1,这个叫快恢复

所以发送多大数据，是由流量控制和拥塞控制一起决定

## 心跳包的设计

协议头字段：包体，用于时间同步

（实现）定时器定时监测：在处理海量并发连接怎么处理：
时间轮算法：这是管理海量连接心跳的最优解。我们可以维护一个环形数组（例如 60 个格子，代表 60 秒）。通常是3次心跳包，时间阈值自己设定

- 每秒钟指针向前移动一格，并销毁该格子中所有的“过期连接”。
- 当某个连接有数据读写或收到心跳包时，将其从当前格子移出，投递到指针前方的第 $N$ 个格子（$N$ 为超时时间）。
- **优势**：添加、删除、刷新连接的时间复杂度均为 $O(1)$，极大地减轻了 CPU 负担。

TCP Keepalive保活
TCP Keepalive 是内核自带的传输层保活机制，

**灵活性极差（全局性强）**：虽然可以通过系统调用为单个 Socket 设置，但默认的系统级参数（如 Linux 默认的 `tcp_keepalive_time = 7200`）长达 2 小时，无法满足秒级探活的需求。

**无法检测应用层死锁**：**这是最致命的缺点。** TCP Keepalive 是由操作系统内核响应的。如果业务进程发生死锁（比如误用死锁、线程卡死）、内存耗尽导致进程僵死，此时操作系统的内核依然健在，它仍会正常回复对方的 TCP Keepalive 探测包。这会导致对端误认为“连接健康”，但实际上业务早已不可用。

**无法穿透某些中间件**：部分敏感的防火墙、代理服务器（如高配版的 NAT 网关）可能会过滤掉不带应用层数据的 TCP 探测包。

## 什么是断点续传：

断点续传就是**文件传输中途中断（断网、程序退出、闪退）后，下次传输不用从头重发，从上次已经传输完成的位置继续发送 / 接收**，节省带宽与时间。

断点续传本质是记录文件已传输的字节偏移，中断后下次从偏移位置继续传输。

首先客户端记录断点偏移量，首次没有记录就从 0 开始；建立连接时把文件名、文件总大小、起始偏移发给服务端。

服务端打开目标文件，通过 lseek 定位到对应偏移位置，客户端分片读取文件后续内容发送，接收端在对应位置写入数据，每传输一块就落地保存断点信息防止再次断连。

传输结束删除临时断点文件，最后可以通过 MD5 校验文件完整性。Linux 下主要依靠文件 lseek 系统调用实现指针跳转，TCP 协议适合稳定续传，还可以结合 mmap 零拷贝优化大文件传输效率。

## 包的序列化和反序列化

在网络编程中，包的序列化（Serialization）**和**反序列化（Deserialization）是极其核心的环节。简单来说：

- **序列化**：把内存里的数据结构或对象，转换成一段**连续的、线性的字节流（Byte Stream）**，以便通过网络发送（或存入文件）。
- **反序列化**：接收端拿到这段线性的字节流后，按照约定的规则，把它重新解析、还原成内存中的数据结构或对象。

你可能会问：**为什么不能直接把内存里的数据 `send` 过去？** 比如，直接把一个 `struct` 的首地址传给 `send` 函数发送，接收端直接拿一个同样类型的 `struct` 指针强转并接收，这不行吗？

在极其严苛的同构环境下（同一台机器、同一个编译器、相同的编译选项），这偶尔能跑通，但在实际的网络开发中，这绝对是灾难，原因有三：

### 1. 指针与内存地址的失效

假设你的结构体里包含指针，比如一个指向堆内存的字符串 `char* name`，或者你用到了一些包含动态内存分配的高级特性（这就好比浅拷贝）。当你把这个结构体直接发到网络上时，你发送的仅仅是 `name` 这个指针存储的**本地内存地址（一个十六进制数字）**。 当另一台机器（或另一个进程）收到这个包时，那个内存地址对它来说是完全无意义的，甚至会导致段错误（Segmentation fault）。**序列化的核心任务之一，就是把指针背后的实际内容（也就是发生一次深拷贝）提取出来，平铺填入到线性的发送缓冲区中。**

### 2. 内存对齐（Memory Alignment）与字节填充

为了提高 CPU 的访问效率，编译器会自动对结构体进行内存对齐。 比如一个包含 `char`（1字节）和 `int`（4字节）的结构体，实际上在内存中可能占据 8 个字节，中间被填充了 3 个毫无意义的空白字节。 不同的操作系统、不同的 CPU 架构（32位 vs 64位）、甚至同一个编译器的不同优化级别，其内存对齐的规则都可能不同。如果不做序列化直接发送，接收端直接按自己的对齐规则去解析，数据完全是对不上的。

### 3. 字节序（Endianness）的差异

不同架构的 CPU 存储多字节整数的方式不同。x86 架构通常是**小端序（Little-Endian）**（低位字节存在低地址），而网络传输标准规定使用**大端序（Big-Endian）**。 序列化通常会包含一个动作：将主机的字节序转换为网络字节序（比如使用 `htonl`, `htons` 等函数），反序列化时再从网络字节序转回主机字节序，以此抹平不同机器的硬件差异。

## epoll 的核心运行机制

`epoll` 是 Linux 环境下高性能网络编程的核心，旨在解决大规模并发连接下的 I/O 效率问题（即 C10K 问题）。相较于早期的 `select` 和 `poll`，`epoll` 在内核实现上进行了根本性的优化。

`epoll` 的高效主要依赖于其内核中的三个核心数据结构和对应的系统调用：

1. **`epoll_create`（创建实例）**：

   在内核中创建一个 `eventpoll` 对象。这个对象包含了两个重要的数据结构：

   - **红黑树（Red-Black Tree）**：用于高效管理和存储所有被监听的 Socket 文件描述符（FD）。插入、查找、删除的时间复杂度均为 $O(\log n)$。
   - **双向链表（Ready List）**：用于存放已经就绪（有事件发生）的 FD。

2. **`epoll_ctl`（事件注册）**：

   将需要监听的 Socket 添加到红黑树中，并为该 FD 注册一个**回调函数**。当网卡接收到数据并通过中断通知内核时，内核会调用这个回调函数，将该 FD 挂载到就绪链表中。

3. **`epoll_wait`（等待事件）**：

   应用程序调用此接口获取事件。`epoll_wait` 不需要像 `select` 那样遍历所有被监听的 FD，它只需要检查**就绪链表**是否为空。如果有就绪事件，直接将链表中的数据拷贝到用户空间并返回。这就使得 `epoll` 的性能不会随着监听 FD 数量的增加而线性下降。







## 边缘触发 (ET) 和水平触发（LT）：

`epoll` 支持两种事件触发模式：水平触发（Level Triggered, 默认模式）和边缘触发（Edge Triggered）。它们的本质区别在于**内核唤醒应用程序的时机不同**。

| **特性**     | **水平触发 (LT - Level Triggered)**                          | **边缘触发 (ET - Edge Triggered)**                           |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **触发条件** | 只要缓冲区中有数据（或缓冲未满），就会一直触发。             | 只有当状态发生**变化**时（例如新数据到达，或缓冲区由满变不满），才会触发一次。 |
| **处理逻辑** | 应用程序可以不一次性读写完所有数据，下次调用 `epoll_wait` 依然会返回该 FD。 | 应用程序**必须**在一个循环中将数据全部读写完，否则剩余数据不会再次触发事件，导致数据滞留或连接假死。 |
| **编程难度** | 较低，容错率高。                                             | 较高，需要严谨的循环读写和状态判断。                         |
| **系统开销** | 较高（可能产生大量的重复唤醒和系统调用）。                   | 较低（减少了 `epoll_wait` 的调用次数），适合极高并发场景。   |

### 为什么一般会设置成非阻塞（Non-blocking）I/O？

在高性能服务器架构中，将 Socket 设置为非阻塞是标准做法，**特别是在使用 ET 模式时，非阻塞 I/O 是强制要求的**。

**1. ET 模式下的死锁避免（核心原因）**

在边缘触发模式下，因为内核只在数据到达的瞬间通知一次，所以你必须在一个 `while` 循环中不断调用 `read()` 或 `write()`，直到把缓冲区榨干。

- **如果使用阻塞 I/O**：当循环读到最后，缓冲区为空时，最后一次 `read()` 调用会直接**阻塞**当前的线程。这就意味着当前线程被挂起，无法返回去调用 `epoll_wait` 处理其他数以万计的并发连接，整个服务器的并发能力瞬间瘫痪。
- **如果使用非阻塞 I/O**：当缓冲区为空时，最后一次 `read()` 会立即返回 `-1`，并设置 `errno` 为 `EAGAIN`（或 `EWOULDBLOCK`）。这个信号告诉应用程序：“数据已经读完了，你可以安全地退出循环，回到 `epoll_wait` 去监听其他事件了。”

## epoll为什么在高并发时性能更好

面试官问的是epoll在高并发场景下比select/poll性能好的底层原理。要从两个维度回答：数据结构的差异和事件通知机制的差异。数据结构上，epoll用红黑树管理fd，增删改查O(log n)，而select/poll每次都要拷贝整个fd集合，且内核要线性遍历O(n)。事件通知机制上，epoll是事件驱动的，设备驱动在有数据时通过回调把fd挂到就绪链表上，epoll_wait只需遍历这个很小的就绪链表；而select/poll每次都要全量扫描所有fd。回答时先定好“事件驱动 vs 轮询”这个基调，再用红黑树和就绪链表作为支撑细节。

高并发下epoll的性能优势还有一个被忽略的点——内存拷贝。select在每次调用时，都要把fd集合从用户态拷贝到内核态，返回时再拷贝回来的结果。当fd数量上万时，这个拷贝本身就很重。poll用了链表但拷贝问题同样存在。epoll的核心思路是把频度高的“查询”和频度低的“增删改”分开处理：增删改用epoll_ctl，次数少，每次操作红黑树O(log n)；查询用epoll_wait，次数多，每次只遍历就绪链表O(活跃数)。这个分离设计是它能扛住大并发量的精髓。在我们的车载系统里，一个车上跑的传感器可能有十几个，fd总数不多，但结合客户的调度系统来看服务器端的连接数，用epoll的优势就体现出来了。

```c++
#include <queue>
#include <mutex>
#include <condition_variable>
#include <memory>

template<typename T>
class ThreadSafeQueue {
private:
    mutable std::mutex mtx_;                // 互斥锁，保护内部队列
    std::queue<T> data_queue_;              // 底层数据结构
    std::condition_variable data_cond_;     // 条件变量，用于阻塞和唤醒线程

public:
    ThreadSafeQueue() = default;
    
    // 禁用拷贝构造和赋值操作（因为锁通常是不可拷贝的）
    ThreadSafeQueue(const ThreadSafeQueue&) = delete;
    ThreadSafeQueue& operator=(const ThreadSafeQueue&) = delete;

    // 1. 入队操作 (生产者调用)
    void push(T new_value) {
        {
            // 加锁保护临界区
            std::lock_guard<std::mutex> lock(mtx_);
            data_queue_.push(std::move(new_value));
        }
        // 唤醒一个正在等待出队的消费者线程
        // 注意：notify 通常放在锁的作用域之外，避免消费者被唤醒后立刻又因为拿不到锁而阻塞
        data_cond_.notify_one(); 
    }

    // 2. 阻塞式出队 (消费者调用)
    // 如果队列为空，线程会被挂起等待，直到有新数据到来，避免 CPU 空转
    void wait_and_pop(T& value) {
        std::unique_lock<std::mutex> lock(mtx_);
        
        // wait 会在 lambda 表达式返回 false 时释放锁并挂起线程
        // 当被 notify 唤醒时，会重新尝试获取锁，并再次检查条件（防止虚假唤醒）
        data_cond_.wait(lock, [this]{ return !data_queue_.empty(); });
        
        value = std::move(data_queue_.front());
        data_queue_.pop();
    }

    // 3. 非阻塞式出队
    // 尝试获取数据，如果有就返回 true，如果没有就立即返回 false，不阻塞
    bool try_pop(T& value) {
        std::lock_guard<std::mutex> lock(mtx_);
        if (data_queue_.empty()) {
            return false;
        }
        value = std::move(data_queue_.front());
        data_queue_.pop();
        return true;
    }

    // 4. 判断队列是否为空
    bool empty() const {
        std::lock_guard<std::mutex> lock(mtx_);
        return data_queue_.empty();
    }
};
```

```c++
#include <atomic>
#include <cstddef>

// 跨平台 pause 指令,提示CPU当前线程处于自旋等待状态，减少功耗和总线争用
inline void cpu_pause() {
#if defined(__x86_64__) || defined(_M_X64) || defined(__i386__) || defined(_M_IX86)
    __builtin_ia32_pause();//
#elif defined(__aarch64__) || defined(_M_ARM64)
    asm volatile("yield" ::: "memory");
#else
    std::this_thread::yield();
#endif
}

template <typename T, size_t Cap>
class MPSCQueue {
    // 缓存行对齐，避免 false sharing
    alignas(64) std::atomic<size_t> head{ 0 };  // 消费者读取位置
    alignas(64) std::atomic<size_t> tail{ 0 };  // 生产者写入位置
    alignas(64) std::array<T, Cap + 1> buffer;  // 环形缓冲区，+1 用于区分空和满
    alignas(64) std::array<std::atomic<bool>, Cap + 1> ready;  // 槽位就绪标志

    // 计算下一个位置，环形缓冲区回绕
    static constexpr size_t next_pos(size_t pos) {
        return (pos + 1) % (Cap + 1);
    }

public:
    // 构造函数：初始化所有 ready 标志为 false
    MPSCQueue() {
        for (auto& r : ready)
            r.store(false, std::memory_order_relaxed);
    }

    // 生产者调用：多线程安全
    bool push(const T& val) {
		size_t pos, next;// 生产者需要先抢占一个槽位，确保不会和其他生产者冲突

        // 第一步：用 CAS 抢占槽位
		//通过底层指令来实现原子操作，避免了锁的开销，
        
        do {
            //轻量读取，
            pos = tail.load(std::memory_order_relaxed);
            next = next_pos(pos);

            // 检查队列是否已满
            if (next == head.load(std::memory_order_relaxed))
                return false;
        } while (!tail.compare_exchange_weak(
            pos, next,
            std::memory_order_relaxed,
            std::memory_order_relaxed));
		//compare_exchange_weak（）函数尝试将 tail 从 pos 更新为 next，如果成功返回 true，表示抢占成功；如果失败返回 false，表示有其他生产者抢占了这个槽位，需要重新加载 tail 并重试。
        // 第二步：写入数据（此时我们独占这个槽位）
        buffer[pos] = val;

        // 第三步：标记槽位就绪，使用 release 确保数据写入对消费者可见
        ready[pos].store(true, std::memory_order_release);

        return true;
    }

    // 消费者调用：单线程
    bool pop(T& val) {
        size_t pos = head.load(std::memory_order_relaxed);

        // 检查队列是否为空
        if (pos == tail.load(std::memory_order_acquire))
            return false;

        // 自旋等待数据就绪
        // 槽位已被生产者抢占，但数据可能还未写入完成
        while (!ready[pos].load(std::memory_order_acquire))
            cpu_pause();

        // 读取数据
        val = std::move(buffer[pos]);

        // 清除就绪标志
        ready[pos].store(false, std::memory_order_relaxed);

        // 推进 head，release 确保上述操作对生产者可见
        head.store(next_pos(pos), std::memory_order_release);

        return true;
    }
};
```

无锁方案or   concurrentqueue库函数

在高并发、低延迟（如交易系统、音视频流媒体、网络套接字数据分发）场景下，必须消除传统锁引起的上下文切换和线程挂起。

无锁队列几乎无一例外地基于环形缓冲区（Ring Buffer）实现，并利用 CPU 的 **CAS（Compare And Swap）** 原子操作。

- **单生产者-单消费者（SPSC - Single Producer Single Consumer）**：
  - **最快、最简单的无锁场景**。完全不需要 CAS。
  - **原理**：维护两个原子指针（或索引） `head` 和 `tail`。生产者只修改 `tail`，消费者只修改 `head`。读写完全并行。
  - **C++ 优化**：利用 `std::memory_order_release` 和 `std::memory_order_acquire` 建立内存屏障（Memory Barrier），防止 CPU 指令重排，确保数据可见性，同时榨干硬件性能。

- **多生产者-多消费者（MPMC - Multi-Producer Multi-Consumer）**：
  - **工业界代表：Disruptor（Java）、Moodycamel ConcurrentQueue（C++ 标杆）**。
  - **原理**：每个槽位（Slot）引入一个状态标记（或版本号 `sequence`）。
    - **生产者**：通过 CAS 原子地将 `tail` 增加 1，抢占一个槽位。抢到后，检查该槽位的版本号是否允许写入。写入完成后，原子地更新槽位状态。
    - **消费者**：通过 CAS 原子地将 `head` 增加 1，抢占一个读取资格。读取完后，将槽位版本号更新，标记为可重新写入。

无锁队列ABA问题，在多线程并发情况下在进程CAS比较时它的典型问题是 ABA——值从 A 变成 B 又变回 A，CAS 一比还以为没变过。非指针场景下（比如计数器）ABA 一般不是问题，但链表场景里被回收的节点可能被重用，会出大问题。解决方案是带版本号的 CAS：比如用 64 位整数，高 32 位存版本号、低 32 位存指针，每次改版本号加一，这样就算值变回 A 版本号也对不上。

如何处理队列满的场景？1.阻塞等待，生产者线程挂起，无锁自旋，调用`std::this_thread::yield()` 让出 CPU 时间片，或者轻量级休眠。2.覆盖老数据。股票行情、自动驾驶中的车速传感器数据

队列用了互斥锁，多线程访问仍然是串行的，如何进一步优化？
          单个互斥锁保护一个队列时，临界区内确实是串行的。如果它成为瓶颈，我会先做低风险优化：把任务按连接、hash或线程编号分片到多个队列，降低竞争；入队和出队做批量操作，减少加锁次数；确保业务执行不在锁内。如果仍不满足，再考虑基于CAS的MPSC或MPMC无锁队列，但要同时处理ABA、内存序和对象生命周期问题。

## UDP穿透

UDP穿透核心思想是利用处于公网服务器，让处于不同私网的客户端互相获取对方公网ip和端口，然后直接 向对方发送各自的NAT映射表，建立通信

1. **登录与协助：** 客户端 A 和 B 分别向处于公网的服务器（Server）发送 UDP 登录包。
2. **交换地址：** 服务器因为在公网，能直接看到 A 和 B 的公网 `IP:Port`。服务器把 A 的公网地址告诉 B，把 B 的公网地址告诉 A。
3. **A 向 B 打洞：** A 尝试向 B 的公网地址发送一个 UDP 包。这个包大概率会被 B 的 NAT 设备丢弃。**但是**，这个操作让 A 的 NAT 设备记录了：*‘A 曾经向 B 的公网地址发过包’*。这就为 B 开辟了一道绿灯（打洞成功）。
4. **B 向 A 连通：** 紧接着，B 也向 A 的公网地址发送一个 UDP 包。因为 A 的 NAT 已经给 B 留了‘绿灯’，这个包能顺利到达 A。此时，B 的 NAT 也会为 A 开绿灯。

至此，双向通道打通，A 和 B 之后就可以脱离服务器，直接进行 P2P 穿透通信了。”

## vld内存泄漏检查：

C++ 常见内存泄漏主要有：

1. 手动 `new/malloc` 忘记释放；

2. 指针重新赋值，丢失堆内存地址；

3. 类缺少析构函数，或基类析构非虚导致子类内存不释放；

4. 容器存放裸指针，只清空容器不释放堆内存；

5. `shared_ptr` 循环引用，引用计数无法归零；

6. 异常、分支、跳转语句跳过释放逻辑；

7. 文件、Socket 等系统句柄未关闭造成资源泄漏。

   解决主要依靠 RAII、智能指针、保证析构正确、规范编码。

##  线程池的核心设计原理

一个标准线程池的核心组件可以抽象为以下三部分：

1. **任务队列（Task Queue）：** 一个线程安全的先进先出（FIFO）队列，用来存放等待处理的任务（通常是 `std::function`）。
2. **工作线程池（Worker Threads）：** 一组长期驻留、不断从任务队列中取出任务并执行的消费者线程。
3. **同步机制（Synchronization）：** 互斥锁（`std::mutex`）用于保证队列的线程安全；条件变量（`std::condition_variable`）用于在队列为空时让工作线程休眠，在有新任务时唤醒它们。

----------------------------------------------------------------------------------

线程池设计要点：

\- 核心线程数 vs 最大线程数：核心线程常驻，超过核心的线程空闲后回收；

\- 任务队列：无界队列 vs 有界队列（防止 OOM）；

\- 拒绝策略：队列满时的处理（丢弃、抛异常、调用者执行）；

\- IO 密集型 vs CPU 密集型：线程数设置不同；

\- 优雅关闭：停止接收新任务，等待现有任务完成。

## 线程池自动扩容/缩容：



 原生线程池的扩容相对“迟钝”。它必须等到队列被塞满后才会去创建非核心线程。如果是 CPU 密集型任务还好，但在 I/O 密集型场景下，这会导致请求堆积在队列中，响应时间变长。



线程在通过 `workQueue.poll(keepAliveTime, TimeUnit)` 获取任务时，如果在超时时间内没有获取到任务，就会返回 null。工作线程（Worker）拿到 null 后，就会执行退出清理逻辑。

常见的扩缩容指标主要有三类。

### ① 基于任务队列长度（最常用、最灵敏）

队列是最直接反映线程池压力的“蓄水池”。

- **扩容阈值（Up-Threshold）：** * **设计逻辑：** 当队列中等待的任务数持续超过一定比例，说明当前核心线程（Core Pools）已经无法跟上任务到达的速度。
  - **推荐阈值：** 队列利用率 $\ge 70\% \sim 80\%$，或者队列中连续 $N$ 秒内的等待任务数超过一个绝对值（如 `QueueCapacity * 0.8`）。
- **缩容阈值（Down-Threshold）：**
  - **设计逻辑：** 当队列几乎为空，且非核心线程处于空闲状态时。
  - **推荐阈值：** 队列利用率 $\le 10\% \sim 20\%$，或者非核心线程的空闲时间超过设定的 `keepAliveTime`（通常设为 30s 到 60s）。

### ② 基于 CPU 与系统负载（资源边界）

作为**熔断**或**限制扩容**的辅助条件，防止盲目扩容导致线程上下文切换（Context Switch）雪崩。

- **扩容限制：** 即便队列满了，如果当前机器的 **CPU 使用率 $\ge 80\%$** 或 **Load Average 远超 CPU 核心数**，应**禁止继续扩容**非核心线程，转而触发拒绝策略或降级，因为此时增加线程只会加剧 CPU 争抢。

### ③ 基于任务平均等待时间（对延迟敏感的业务）

- **设计逻辑：** 有些业务队列很短，但单个任务耗时长。此时监控队列长度不准确，需要监控任务在队列中的**排队延迟（Queue Delay）**。
- **推荐阈值：** 当 P99 或 P95 的排队等待时间超过业务可接受的 TP99 响应时间的 $20\%$ 时，触发扩容。





## 守护进程的创建：

**第一次 `fork()`：** 父进程退出，子进程继续。这保证了子进程绝对不是原来的组长进程（这是调用 `setsid()` 的先决条件）。

**调用 `setsid()`：** 子进程创建新会话、新进程组，脱离终端控制。

**第二次 `fork()`（可选但推荐）：** 子进程再次 `fork()` 出孙子进程，然后子进程退出。因为孙子进程不是“**会话首进程”**，根据系统规定，非会话首进程永远无法重新打开或绑定一个新的控制终端。这为守护进程上了一道“双保险”。



## 惊群效应：

**惊群效应算是高并发网络编程里的经典通病**

## Qt信号与槽机制的作用

**信号槽**：Qt 实现**对象间解耦通信**的机制
核心依赖：Qt 元对象系统 (Meta-Object System)

**Q_OBJECT 宏**：开启元对象能力（必须写，否则信号槽失效），禁用拷贝和赋值

**MOC 编译器**：Qt 专属预编译器，解析 `signals:` `slots:`，**自动生成代码**

运行时类型信息：动态查找信号 / 槽名字、参数、对象

信号与槽是Qt实现对象间通信的核心机制。当某个事件发生时（如按钮点击），对象会发射信号；槽则是响应信号的普通成员函数。这种机制松耦合地连接了发送者和接收者，无需知道对方具体细节。

```c++
connect(sender, &SenderClass::signalName,
        receiver, &ReceiverClass::slotName);
```

QT中信号触发后走什么链路？
     主要取决于信号槽的连接方式
     同一线程默认采用直连，本质函数指针直接调用，
 1.发射信号：emit mySignal(arg);emit本质上是一个空宏，MOC生成函数实现
 2.再moc.cpp生成函数实现，把参数打包成指针数组
 3.调用QMetaObject::activate激活静态函数，传入发送者指针，信号索引，参数包裹
 4.查找发送者ConnectionList连接表，遍历槽
5.通过函数指针直接调用
6.回到emit发送信号的下一行代码
    不同线程异步的，采用投递事件加深拷贝

第五个参数决定槽函数在那个线程，何时执行：

- **默认 `AutoConnection`**：99% 场景够用
- **跨线程更新 UI**：用 `QueuedConnection`（或默认自动）
- **需要同步返回值**：用 `BlockingQueuedConnection`（注意死锁）
- **防止重复绑定**：加 `UniqueConnection`

## QT对象树机制：

- 在Qt中，通过设置父对象（如 `QWidget` 或 `QObject` 的 `setParent()` 或构造函数传参），子对象会被添加到父对象的对象树中。
- **当父对象被销毁时，它会先自动销毁其所有子对象**，从而形成自顶向下的自动析构链。这简化了内存管理，开发者无需为每个控件单独 `delete`，只需保证父对象适当释放即可，有效避免内存泄漏。即使子类对象先被释放也不会double Free

对于继承自`QWidget` 的界面元素，对象树不仅代表**内存所有权**，还代表**视觉上的层级与裁剪**：
**绘制坐标**：子组件（如按钮）的坐标系统相对于父组件（如主窗口）。
**事件传递**：未处理的事件（如键盘、鼠标事件）会沿着对象树向上层传递（事件冒泡）。  
**渲染与隐现**：隐藏或销毁父组件时，其所有的子组件也会自动隐藏或销毁。

##  **`QApplication::exec()`**

启动事件循环，QApplication 是整个 Qt 程序的调度总管，exec () 就是开启总管持续监听、分发事件的总开关。

## 帧率和码率：

帧率：每秒画面刷新多少张图片
码率 ：每秒需要传输多少比特的数据量

| 维度     | 帧率 FPS                                                     | 码率 Bitrate             |
| -------- | ------------------------------------------------------------ | ------------------------ |
| 控制对象 | 一秒多少帧画面                                               | 每一帧画面有多清晰       |
| 影响体验 | 画面流不流畅                                                 | 画面清不清晰             |
| 带宽占用 | 帧率越高，同等画质下带宽越大                                 | 码率直接决定最低带宽需求 |

## 声音采集原理和模数转换：

声信号-->模拟电信号---->模数转换（ADC）：采样-量化-编码-存储
采样：模拟信号是一条连续曲线，ADC 按照固定时间间隔**截取瞬时电压值**，这个间隔频率就是**采样率**。**采样频率必须 ≥ 2 倍信号最高频率**，否则会发生**混叠失真**，声音畸变。
量化：量化就是把电压整个取值**区间平均分成 N 份阶梯**，把当前电压就近匹配到某一个阶梯刻度，用整数编号代表幅值。量化位深：8bit：
28=256 级，音质粗糙，多用于早期语音
16bit：216=65536 级，CD 标准，日常音乐够用
24bit：专业录音，动态范围更大，捕捉极轻 / 极强声音
编码：量化值转成PCM脉冲编码调制格式二进制数据

调用系统音频API：linux用ALSA,Windows用WASAPI，跨平台选PortAudio或RtAudio,配置采样率，位深，通道数后从回调获取PCM数据



高品质音频为何需要44.1kHz以上？
     人耳可听频率上限约 20 kHz，奈奎斯特采样定理：采样率至少要大于最高频率的 2 倍，即至少约 40 kHz，44.1 kHz 留出了抗混叠滤波器的过渡带，因此成为 CD 音频标准.

什么是PCM（脉冲编码调制）
PCM 通常是无压缩、原始音频数据，WAV 往往只是给 PCM 加了文件头。
采样率：如 `44100 Hz`、`48000 Hz`；
位深：如 `16 bit`、`24 bit`，决定量化精度和动态范围；
声道数：单声道 `1`、立体声 `2`；
样本格式：`S16LE`、`S32LE`、浮点 `FLT` 等；
数据排列：交错格式 `LRLR...`，或平面格式 `LLLL... RRRR...`

```
字节数 = 时长 × 采样率 × 声道数 × 位深 / 8
```

每个采样点用多少位表示（位深）？
   每个采样点需要多少位由量化精度决定，称为位深。常见 PCM 用 16 bit 表示一个采样点，专业录音常用 24 bit，音频处理链路常用 32 bit 浮点。位数越多，可表示的幅度等级越多，量化误差和量化噪声越小，动态范围越大，但数据量也更大。**采样率**：一秒采多少次，例如 48 kHz；
**位深**：每次采样用多少位，例如 16 bit；
**比特率**：`采样率 × 位深 × 声道数`

在V4L2中时间戳处理：
驱动在buffer.flag中通过标志位告诉你时间戳用的是哪个时钟:

| 标志                                     | 时钟                    | 特点                                                |
| ---------------------------------------- | ----------------------- | --------------------------------------------------- |
| `V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC` 置位 | `CLOCK_MONOTONIC`       | 从系统启动起单调递增，不受 NTP 校时、用户改时间影响 |
| 未置位                                   | 通常是 `CLOCK_REALTIME` | 墙钟时间，可能被 NTP 跳变、手动修改                 |

```c++
// 判断这一帧的时间戳是否为单调时钟
const bool timestampMonotonic =
    (buffer.flags & V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC) != 0;

// 无论是否单调，帧数据照存不误（不丢弃）
raw.write(...);

// 但在 CSV 里用 0/1 明确标记时钟类型
metadata << frame << ',' << videoPtsNs << ',' << timestampMonotonic << ',' << ...;
```

音频采集（ALSA 等）通常也使用单调时钟。所以：

- **视频 = 单调时钟，音频 = 单调时钟** → 同一时钟域，可以直接相减做同步 ✅
- **视频 = 墙钟时间，音频 = 单调时钟** → 不同时钟域，相减无意义 ❌
- 即使两边都是墙钟，中途一次 NTP 跳变就会让差值突变 ❌



音频是连续流，视频时离散帧：
音频时间戳的计算**不能靠系统当前时间点（`gettimeofday` 等）逐帧去打标记**（因为系统调度会导致抖动），而是必须**依据采样的累计样本数（Samples）严格推算**。
采集刚启动，收取第一帧PCM数据：

**认清数据本质（连续的流）**：因为音频是连续的 PCM 字节流，没有视频那种天然的“画面帧”边界，所以绝对不能用对待视频的方式（逐帧打系统时间）去对待音频。

**确立时间轴策略（锚点 + 递推）**：

- **第一步**：抓住第一个有效数据块，利用底层 API（如 ALSA 的硬件状态和单调时钟）精准推算出第一帧的**绝对物理时间**，作为时间锚点（Anchor）。
- **第二步**：后续所有数据彻底抛弃系统时间查询，**只相信采样率**。通过 `累计采样数 / 采样率` 来做绝对平滑的线性递增，生成最终的 PTS。

**守住健壮性底线（应对物理与环境异常）**：

- **断流/溢出（Overrun）**：必须有监控机制，一旦发现丢数据，立刻斩断旧的时间线（Start New Epoch），重新对齐新锚点，防止错位累积。

  在采集端遇到 **Overrun (-EPIPE)** 时，底层的处理必须分为两步：

  1. 调用 `snd_pcm_prepare()` 恢复驱动状态；
  2. **时间戳修复**：若是实时直播场景，重新捕获当前单调时间作为新锚点，防止时间轴滞后；若是本地录制场景，可根据系统时间差计算缺失点数并填充静音帧，保持时间轴连续。”

- **时钟漂移（Clock Drift）**：理解物理晶振的误差，持续监控硬件时间与理论时间的差值，在必要时（偏差过大）通过重采样（Resampling）或音画同步策略进行微调。

  ```
  第一次硬件时间：H0
  第 N 个音频 frame 的当前硬件时间：HN
  按采样率推导的理论时间：P_N = H0 + N / sampleRate
  
  drift = HN - P_N
  ```

采集总结：
1.设备的枚举
2.分辨率，像素格式，帧率的设置，通过`VIDIOC_S_FMT` 是协商，不保证驱动接受请求的宽高或像素格式
3.V4L2设置4个缓冲区，通过mmap映射减少拷贝，ALSA环形缓冲区overrun,进行恢复，发生 overrun 后数据已不连续，因此新增 `epoch`，不伪造连续 PTS。写入文件操作可以新建操作线程，目的就是防止缓冲队列造成延迟升高
4.时间戳处理，确保视频音频都为本地时间域，音频是字节流，通过采样率递增来处理PTS



## 编码学习：

YUV420P的内存布局：
采样比例（4：2：0）： 每 4 个 Y 分量共享 1 个 U 分量和 1 个 V 分量
Y 分量的分辨率：`width × height`
U 分量的分辨率：`(width / 2) × (height / 2)`
V 分量的分辨率：`(width / 2) × (height / 2)`

```c++
YUV420P 整体内存（或由三个指针分别指向）：

data[0] 指向 Y 平面:
┌───────────────────────────┐
│ Y Y Y Y Y Y Y Y Y Y Y Y   │ (height 行，每行 width 个 Byte)
│ Y Y Y Y Y Y Y Y Y Y Y Y   │
└───────────────────────────┘

data[1] 指向 U 平面:
┌─────────────┐
│ U U U U U U │ (height/2 行，每行 width/2 个 Byte)
└─────────────┘

data[2] 指向 V 平面:
┌─────────────┐
│ V V V V V V │ (height/2 行，每行 width/2 个 Byte)
└─────────────┘
```

datat[]和linesize[]:
`uint8_t *data[8]`：指针数组，保存每个平面的**起始内存地址**。

`int linesize[8]`：整数数组，保存每个平面**一行数据占用的字节数（stride / 跨度）**。

总结：
1.**布局：** YUV420P 是 **Planar** 格式，内存中依次独立存放 Y、U、V 三个平面，分别对应 `data[0]`、`data[1]`、`data[2]`。
**2.跨度关系：** `data[i]` 决定平面的**起始位置**，`linesize[i]` 决定寻址时**跨越一行需要的内存字节步长**。
**3.对齐填充：** `linesize[i] >= 有效宽度`，多出来的部分是内存对齐用的 Padding，处理图像数据时必须通过 `y * linesize[i]` 来精确计算行偏移。
4.4个像素点6字节（YYYYUV），1像素点1.5字节，所以一帧大小为 `width * height * 3 / 2`，所以不能直接memcpy视频帧
5.根据高度着行拷贝，源端可能也有自己的stride,填充，也需要处理

### GOP过大过小？

- GOP 过大（关键帧间隔长）
  - **优点**：I帧数量减少，P/B帧比例增加，视频压缩率更高，能有效减小文件体积并节省网络带宽。
  - **缺点**：随机访问（拖拽进度条）响应变慢，因为播放器必须从上一个 I帧 开始解码到目标位置；容错能力弱，网络丢包后需要等待更长时间（直到下一个 I帧）才能恢复画面；GOP 后部帧可能出现画面失真。
- GOP 过小（关键帧间隔短）
  - **优点**：Seek 响应速度快，画面拖动流畅；抗丢包能力强，网络波动后能迅速恢复画面。
  - **缺点**：I帧 数量增多，导致视频压缩率下降，文件体积变大，对网络带宽的消耗显著增加。

为什么需要CRF（Constant Rate Factor，恒定质量因子）？
        传统CBR(固定码率)或普通VBR(动态比特率控制)会给每一秒分配相对固定的数据量：
         1.**静态/简单画面**（如有人在演讲）：浪费了大量码率。
         2.**复杂/高速运动画面**（如游戏、赛车、粒子特效）：码率不够用，导致马赛克或花屏。
        CRF策略：编码器会根据画面的复杂度自动调整压缩率。 
        CRF 的值通常是一个数字，**数值越小，画质越高，文件越大；数值越大，画质越差，文件越小**。
⚠️ **注意：直播不建议直接使用纯 CRF 模式** 因为直播网络需要平稳的带宽，CRF 遇到复杂大动态画面时码率会陡增（突发 Peak 码率），极易引发推流卡顿或丢包。直播通常使用 **CBR** 或者带码率上限的 **VBV（CRF + maxrate + bufsize）**。

![image-20260728214628124](C:\Users\95892\AppData\Roaming\Typora\typora-user-images\image-20260728214628124.png)

| **模式名称**                                   | **机制特点**                                                 | **适用场景**                                                 |
| ---------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **VBR (Variable Bitrate / 动态码率)**          | 设定目标码率和最大码率。简单画面用低码率，复杂画面动态提升至峰值。 | **网络允许一定波动的点播/直播**。比 CBR 节省带宽，画质更好。 |
| **ABR (Average Bitrate / 平均码率)**           | 设定一个目标总平均码率（如 2000kbps），编码器保证整段视频的平均值达标。 | **旧版直播流/离线转码**。控速率不如 CBR 严格，现逐步被 VBR/CRF 替代。 |
| **Constrained Baseline / Capped CRF**          | 带有 **`maxrate` (最大码率)** 和 **`bufsize` (缓冲区大小)** 的 CRF/VBR。 | **最佳实践：高质量直播推流**。既保留了 CRF 根据复杂度分配码率的优势，又设定了“天花板”防止爆网络。 |
| **CBR + Dynamic Downscaling (动态自适应 CBR)** | 根据实时网络丢包/RTT 延迟，由 WebRTC/RTC 引擎动态下发改变 CBR 的目标码率。 | **实时音视频通话 (RTC)**、低延迟互动直播。                   |

总结：码率该怎么设置？
明确场景需求：主要取决**网络带宽**和**画面质量**
1./录制/点播/离线转码场景：CRF,复杂多给码率，简单节省码率,保证压缩率
2.实时直播/RTC音视频通话:对网络波动敏感，优先选择 **Capped VBR（带上限的动态码率）** 或 **CBR（固定码率）**。

**x264/x265（软编）**：CRF 效果最好，支持非常精细的 VBV 缓冲区控制（智能动态 QP）

## H.264压缩技术

H.264，也被称为高级视频编码

| 冗余类型     | 对应技术                      | 核心原理                                                     | 主要应用对象                           | 压缩性质                           |
| ------------ | ----------------------------- | ------------------------------------------------------------ | -------------------------------------- | ---------------------------------- |
| **空间冗余** | 帧内预测（Intra-prediction）  | 利用同一帧内已编码的相邻像素预测当前块的像素值，只记录预测值与实际值的**残差** | I 帧（关键帧）                         | 预测过程无损，残差后续经量化为有损 |
| **时间冗余** | 帧间预测（Inter-prediction）  | 通过运动估计和运动补偿，在参考帧中寻找相似块，记录**运动矢量**和残差 | P 帧（前向预测帧）、B 帧（双向预测帧） | 预测过程无损，残差后续经量化为有损 |
| **视觉冗余** | 变换与量化（整数 DCT + 量化） | 整数离散余弦变换将残差从空间域转为频率域，量化舍弃人眼不敏感的**高频细节** | 所有帧的残差数据                       | **有损压缩**（信息不可逆丢失）     |
| **编码冗余** | 熵编码（CABAC / CAVLC）       | 对量化后的数据、运动矢量等参数重新编码，**高频数据用短码、低频数据用长码** | 所有最终编码参数                       | **无损压缩**（信息完全可逆）       |

DTC离散余弦变换作用：
把图像空间像素，转换成「频率系数」
低频系数：画面主体轮廓、大块色彩（人眼敏感）
高频系数：纹理、发丝、噪点、细节（人眼不敏感）

量化作用：QP（量化参数）
除以一个步长，把大量不重要的高频系数变成0，减少数据量，步长由QP决定
QP 越小，QStep 越小，系数保留完整，像素和原图差距极小，码率高
QP 越大，QStep 越大，大量高频细节归零，画面模糊、色块、马赛克，码率低。

##  时间戳处理和校正:

时间基转换：

采集阶段产生原始时间戳---->编码阶段（对齐编码器time_base）------>强制转换时基到封装容器------>封装FLV

```
av_rescale_q(val, 原时基, 目标时基)
av_packet_rescale_ts(&pkt, 编码器时基, 输出流时基)
```


校正为什么需要呢？

PTS（Presentation Time Stamp，呈现时间戳），告诉播放器什么时间点显示，理想情况下PTS间隔应严格等于1/帧率（如30fps对应约33.3ms）。

但是B帧（双向预测帧）的编码逻辑是**参考“前向 I/P 帧”和“后向 P 帧”来压缩数据**。B帧的解码顺序 ≠ **显示顺序**（必须先解码前后参考帧，才能解出 B 帧）；
但 B 帧的 **PTS 必须对应“显示顺序”的时间点**（否则播放时画面会乱序），所以B帧的解码和显示顺序差，依照DTS可以保证解码顺序，避免画面错乱

时间戳校正的核心目标是**确保视频帧的显示时间（PTS）与音频时间轴严格对齐**尤其在存在B帧、变速、多源拼接等复杂场景下

实际开发中的同步处理流程？

1. **解复用（Demuxing）**：提取音视频的压缩数据包（AVPacket）及原始的 PTS/DTS。

2. **时间基统一（Rescale）**：将音视频的 PTS/DTS 转换到统一的时间基下，消除格式差异。

3. **解码（Decoding）**：将转换后的 Packet 送入解码器，还原为原始帧（AVFrame）。

4. 解码后缓冲与同步（Frame Queue & Sync）

   ：将解码后的 AVFrame 放入缓冲队列。同步模块以音频时钟（Audio Clock）为基准，持续从队列中取出视频帧，比对 

   ```
   Video_PTS - Audio_PTS
   ```

    的差值：

   - 差值大于阈值（视频快了）：让视频渲染线程 Sleep 等待。
   - 差值小于负阈值（视频慢了）：丢弃当前的视频帧，取下一帧追赶。

5. **渲染（Rendering）**：通过同步校验的帧最终交由屏幕或声卡输出。



## PTS丢弃过期帧？

用来处理卡顿和低延迟，内存溢出
1.**体验上**会造成视觉跳帧和卡顿感；

2.**技术上**需要非常小心——如果在解码前误丢了 $I/P$ 等参考帧，会导致后面一整段画面**花屏**；如果在解码后丢，则会消耗无意义的解码算力。
      总结：所以实际工程中，我们通常会**优先丢弃非参考的 B 帧**，或者在延迟较大时**以 GOP 为单位批量丢弃**直接跳到下一个 IDR 帧，甚至采用**微倍速播放**来无感追赶 PTS，而不是简单粗暴地见过期就丢。”



## 时钟漂移：

​          它是指**两个原本同步的时钟，由于运行频率存在微小差异，导致经过一段时间后，它们显示的时间差越来越大，最终“脱节”的现象**

解决：
**1.硬件级统一：共享主时钟**,所有的采集设备都通过物理线缆连接到这个主时钟，强制所有设备使用同一个基准频率。只要大家的“心跳”完全一致，就从根本上消除了时钟漂移。
2.**软件级对齐：音频主导策略**,
3.协议校准，RTCP，发送端发送RTCP SR，计算漂移率，实际物理时间差（墙上时钟）和实际采样音视频时长（硬件采集样本技术/采样率）进行判断漂移多少，所以可以判断同一时刻的音频和视频，如果漂移，做微调补偿
4.**. 缓冲补偿：抖动缓冲区（Jitter Buffer）**
5.**后期修复：重新打戳与重采样**
            在 FFmpeg 的 `libswresample` 库中，可以通过设置 `async` 参数来启用这种基于时间戳的自动补偿机制。重采样器会根据音频时间戳的偏移量，动态地对音频样本进行拉伸或压缩（倍速播放），从而在不改变音调的前提下，让音频去追赶或等待视频





## GOP和P  I  B 帧：

一段码流里，**从一个 I 帧开始，到下一个 I 帧之前的所有帧，合起来就叫一个 GOP**。
为什么一定要划分GOP?
1.播放器起播，拖拽需要
2.网络丢包容错

I帧（Intra-frame，关键帧）：

帧内编码帧，

独立完整画面

，不依赖任何其他帧就能解码出整张图像。

- 原理：只压缩当前画面内部像素，和前后画面无关；
- 大小：体积最大，一张 I 帧≈十几张 P 帧；
- 作用：视频起点、随机拖拽播放、画面刷新基准、容错锚点；
- 场景：播放器拖动进度条时，会跳到最近的 I 帧开始渲染。

P 帧（Predictive-frame，前向预测帧）：

前向预测编码帧，**（运动矢量和差异预测）**

只存和前一帧的差异变化，必须依赖前面的 I 帧 / P 帧才能解码。

- 原理：记录 “相比上一帧，哪些像素动了、动到哪”，不动的像素直接复用前帧数据；
- 大小：体积远小于 I 帧；
- 作用：压缩体积主力，连续画面里大部分都是 P 帧；
- 局限：如果前面参考帧损坏，这一帧画面会花屏、卡顿。

B 帧（双向预测帧）：同时参考**前一帧 + 后一帧**做差值压缩，压缩率最高，但解码计算量更大；直播场景为了低延迟常禁用 B 帧，只留 I+P。

IDR帧（Instantaneous Decoder Refresh，即时解码刷新帧）：
  IDR 帧是一种**特殊且关键的 I 帧**。
     **作用（清除历史依赖）：** 当解码器遇到 IDR 帧时，会立刻清空参考帧缓冲区（DPB）。这意味着 **IDR 帧后面的所有帧，绝对不能跨越 IDR 帧去参考之前的任何帧**。

   **工程意义：** IDR 帧是实现秒开、切台、 Seek（拖动进度条）和抗花屏（防止丢包影响后续画面）的起点。

场景：

直播 / 实时推流

必须保证固定间隔出 I 帧（比如 2 秒一个 I 帧），不然观众切进来、网络波动后无法快速恢复画面；I 帧间隔越长，文件越小，但卡顿恢复越慢。

**剪辑 / 录屏**

I 帧多的视频，拖拽、裁剪、分割速度更快；长 I 帧间隔的视频剪辑容易出现画面黑屏、花屏。

**码率与画质**

同等画质下：单帧体积 I 帧 ≫ P 帧 ≫ B 帧；相同文件大小下，B 帧越多画面越清晰

## RGB和YUV：

两种常见的颜色空间，RGB 是为了方便显示器和摄像头硬件而设计的，而 YUV 是为了高效的网络传输和视频压缩而诞生的。

**Y（Luma 亮度）**：灰度图，决定画面明暗、轮廓，人眼最敏感，信息量最多
Y 通道 ≠ 物理亮度强度，
      Y 只是**编码后的信号值**（0‑255 / 16‑235 / 0‑1023），不是真实物理 cd/m²。
     Y 代表**相对亮度信号**；要得到真实物理强度，还需要色空间（BT.601 / BT.709 / BT.2020）和 Gamma/PQ 曲线解码。

**UV（Chroma 色度 / 色差）**：色彩信息，U 蓝色分量，V 红色分量；人眼不敏感，可以压缩降低分辨率（色度下采样）

```c++

data[0] → Y 平面：亮度
          宽 × 高

data[1] → U 平面：蓝色色度
          宽/2 × 高/2

data[2] → V 平面：红色色度
          宽/2 × 高/2
```

一个视频帧通常流程：
摄像头采集RGB-YUV-H264编码器-NALU码流-RTP包（网络传输）-接收后--- 
-应用层拼装---FFmpeg解码-

RGB：
每个像素的最终颜色，是 **R、G、B 三个通道根据自身颜色深度确定的强度值，叠加混合** 得到的。
    颜色深度：存储每个颜色通道，用多少个 bit 来表示。代表总共有多少级可以表达。位深 = 一把尺子上有多少刻度；刻度越多，渐变越顺滑。
    颜色强度：强度就是光的物理亮度大小，代表实际有多亮。
![image-20260820212045035](C:\Users\95892\AppData\Roaming\Typora\typora-user-images\image-20260820212045035.png)



普通RGB纹理：每个像素包含 3 个字节（R、G、B），是 3 通道。
单通道纹理（R8）：每个像素只保存 **1 个字节（8 位数值，0~255）**，仅仅原样存放 Y / U / V 的原始字节值
把YUV三份原始数据送到GPU显存中，生成3张独立的R8纹理

```c++
GLuint textures[3]; // 分别对应 Y, U, V，R8纹理
glGenTextures(3, textures);
void updateFrame(AVFrame* frame) {
    // 1. 绑定并上传 Y 纹理 (Width x Height)
    glActiveTexture(GL_TEXTURE0);
    glBindTexture(GL_TEXTURE_2D, textures[0]);
    // 内存对齐处理，防止 stride 不对齐导致画面倾斜
    glPixelStorei(GL_UNPACK_ROW_LENGTH, frame->linesize[0]);
    glTexImage2D(GL_TEXTURE_2D, 0, GL_RED, frame->width, frame->height, 0, GL_RED, GL_UNSIGNED_BYTE, frame->data[0]);

    // 2. 绑定并上传 U 纹理 (Width/2 x Height/2)
    glActiveTexture(GL_TEXTURE1);
    glBindTexture(GL_TEXTURE_2D, textures[1]);
    glPixelStorei(GL_UNPACK_ROW_LENGTH, frame->linesize[1]);
    glTexImage2D(GL_TEXTURE_2D, 0, GL_RED, frame->width / 2, frame->height / 2, 0, GL_RED, GL_UNSIGNED_BYTE, frame->data[1]);

    // 3. 绑定并上传 V 纹理 (Width/2 x Height/2)
    glActiveTexture(GL_TEXTURE2);
    glBindTexture(GL_TEXTURE_2D, textures[2]);
    glPixelStorei(GL_UNPACK_ROW_LENGTH, frame->linesize[2]);
    glTexImage2D(GL_TEXTURE_2D, 0, GL_RED, frame->width / 2, frame->height / 2, 0, GL_RED, GL_UNSIGNED_BYTE, frame->data[2]);
}
```



## 视频硬编码软编码：

配置是否写死。
软编码：完全靠CPU运算压缩算法**（H.264/H.265）**，纯软件实现，没有调用专用硬件模块。
硬编码：调用显卡、芯片内置**专用编码硬件模块（ASIC）**，CPU 只做少量调度，压缩计算交给硬件电路。

| 对比维度       | 软编码（软件编码）                             | 硬编码（硬件编码）                                          |
| -------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| 核心本质       | 纯软件算法实现视频压缩，无专用硬件参与         | 调用显卡 / 芯片内置的专用编码硬件模块完成压缩               |
| 执行主体       | 完全由 CPU 承担全部编码运算                    | CPU 仅做调度，核心压缩计算由硬件电路完成                    |
| CPU 占用       | 极高，单路高清编码即可打满 CPU 核心            | 极低，仅少量调度开销，多路并发也不会占用过多 CPU            |
| 编码速度       | 较慢，同画质下速度远低于硬编码                 | 极快，实时编码、多路并发场景优势明显                        |
| 画质与码率控制 | 画质上限高，码率、参数调节粒度极细，灵活性强   | 画质上限略低于专业软编码，精细码率控制能力较弱              |
| 硬件依赖       | 无，任何 CPU 均可运行，无设备限制              | 强依赖对应硬件（NVIDIA/Intel/AMD 显卡、嵌入式芯片）         |
| 兼容性         | 拉满，全平台通用，无兼容性报错风险             | 受硬件型号、驱动版本影响，存在兼容性坑                      |
| 功耗与发热     | 功耗高，CPU 满载运行发热严重                   | 功耗极低，省电、发热小，适合移动端 / 嵌入式设备             |
| 典型编码器     | libx264、libx265（FFmpeg 默认软编码器）        | NVIDIA NVENC（GPU）、Intel QSV、AMD VCE、安卓 MediaCodec    |
| 主流适用场景   | 本地视频压制、专业剪辑转码、追求极致画质的场景 | 直播推流、摄像头实时编码、多路监控转码、嵌入式 / 移动端采集 |



## 音频特性参数：

采样率：每秒对声音的采样次数
通道数/声道布局：如单声道，双声道，多声道
采样位深：指定输入PCM的数据类型，单个采样点用多少bit的存储大小
PCM（码率）=采样率×位深×声道数
麦克风采集 → **PCM 原始数据（采样率 + 位深 + 声道 = 原始码率）**→ **音频编码器压缩（AAC / MP3 / Opus）**→ 压缩后音频码流，再封装打包传输 / 存文件

## 视频核心参数：

分辨率：一帧画面像素宽 × 高
帧率 FPS：每秒播放多少帧画面
像素格式：色彩采样存储格式
分辨率 + 帧率 + 像素格式 → 决定原始码率，再经过编码器压缩，由**编码协议 + 码率 + GOP**控制最终输出码流大小与画质。
摄像头采集 → **YUV 原始数据（分辨率 + 帧率 + 像素格式 = 原始码率）**→ **视频编码器压缩（H.264/H.265/AV1 + 码率 + GOP）**→ 压缩后视频码流，封装打包传输
一帧字节数=width* height*2
YUYV422：**一个像素占用 2 字节**
RGB24：一个像素 3 字节
RGBA：一个像素 4 字节

视频参数在“分辨率/帧率（清晰流畅度）”**、**“码率（网络带宽）”**、**“延迟（B帧与GOP）”**以及**“算力（Preset/Profile）”之间寻找一个符合你业务场景的精密平衡点。

```c++
AVCodecContext *c = avcodec_alloc_context3(codec);
c->width = 1280;
c->height = 720;
c->time_base = (AVRational){1, 30}; // 30 FPS
c->framerate = (AVRational){30, 1};
c->pix_fmt = AV_SAMPLE_FMT_YUV420P;

// 码率与控制模式 (CBR)
c->bit_rate = 1500000; // 1.5 Mbps
c->rc_max_rate = 1500000;
c->rc_min_rate = 1500000;
c->rc_buffer_size = 3000000; 

// GOP 结构配置
c->gop_size = 60;      // 每60帧一个I帧 (2秒)
c->max_b_frames = 0;   // 【关键】禁用B帧，消除前后参考延迟

// 针对实时传输的特定优化字典 (针对 libx264)
AVDictionary *param = NULL;
av_dict_set(&param, "preset", "veryfast", 0);    // 编码速度变快，降低CPU占用
av_dict_set(&param, "tune", "zerolatency", 0);   // 【关键】开启零延迟策略，禁用帧缓存队列
av_dict_set(&param, "profile", "baseline", 0);   // 提高老设备兼容性

avcodec_open2(c, codec, &param);
```

为什么直播，低延迟场景要禁用B帧？
GOP结构	：I P B

1.编码端：编码器需要缓存P帧，等B帧（双向预测帧），多出一帧等待时延
2.解码端：播放器拿到P帧，缓存等B帧解码，然后渲染，增加播放延迟
3.PTS和DTS乱序，播放器需要重排序

但是完全禁用B帧，延迟低，但是同画质码率更高，带宽变高，所以在不同场景对B帧的处理不一样

## SDL负责播放和显示：

**视频渲染**：SDL 封装了底层图形 API（如 Windows 上的 Direct3D，Linux 上的 OpenGL/Vulkan），你只需要把解码后的 YUV 图像数据丢给 SDL，它就能高效地在窗口里把画面画出来。

**音频播放**：SDL 提供了驱动声卡的接口。你把解码后的 PCM 声音数据塞进 SDL 的音频缓存队列里，它就会负责把声音平滑地播放出来。

**事件与定时器**：我们前面提到的**高精度渲染定时器**以及**控制视频帧率的休眠机制**，在很多开源播放器中都是直接利用 SDL 的定时器（如 `SDL_AddTimer`）和事件循环机制来实现的。



## 视频画面花屏你会怎么排查？

1.**网络与传输层排查**:

- **关键帧（I帧）丢失**：视频流中的预测帧（P帧/B帧）依赖关键帧解码。如果网络抖动或丢包导致关键帧丢失，解码器会因无法正确重建图像数据而产生大面积花屏。
- **网络状态检测**：检查网络环境是否稳定。可通过抓包或日志查看重传率（rtRate）、通道占用比（chload）和丢包率。若丢包率不为0或重传率过高，说明网络存在丢包或干扰。
- **带宽与码率匹配**：检查视频流的码率上限是否超过了当前网络带宽，若超出会导致传输瓶颈，引发花屏或卡顿。

2.**编解码与数据层排查**：

- **元数据（Metadata）变化**：视频流中的关键参数（如分辨率、帧率、编码格式）在直播或推流过程中如果发生变化，播放器可能无法及时适应，从而导致解码异常和花屏。
- **Stride与宽高未对齐**：在视频编解码器的Buffer模式下，如果Stride（步幅，即图片在内存中每一行像素数据的存储宽度）与视频实际宽高未对齐，且未进行相应的偏移处理，会导致渲染时数据错位，引发花屏。
- **颜色空间转换错误**：虽然绿屏更多指向颜色空间转换失败，但某些YUV转RGB的矩阵应用错误或UV分量丢失，也可能表现为局部的色彩失真和花屏。

在排查时，建议使用不同的播放器（如VLC、PotPlayer等）播放同一视频源，或者对比其他平台应用播放同一视频的表现。如果问题仅出现在特定播放器或设备上，则多为解码或渲染兼容性问题；如果所有设备均花屏，则应重点排查视频源、编码端或网络传输环节。







## 倍速

视频倍速：调整时间戳，缩短时间间隔，当倍速开的很高时，进行丢帧

音频变速：改变采样点，如果只是单纯地加快 PCM 数据的播放速度（比如采样率加倍），声音的频率就会变高，大叔的声音会变成“小黄人”一样的尖叫声（即失真变调）。因此，音频倍速必须做到“变速不变调”。

### 3.sdp格式说明

sdp(会话描述协议):

## RTSP-over-HTTP 隧道？

正常RTSP流程：
客户端-554端口直接发送RTSP指令（OPTION/DESCRIBE/SETUP/PALY）+RTP音视频裸流
收发用一个socket套接字
但是防火墙路由器拦截554这类非常规端口，放行80（HTTP）端口，于是出现隧道
此时：
1.发送 RTSP 命令用的是**POST 连接 SocketA**
2.接收流媒体数据用的是**GET 长连接 SocketB**
3.**收发不是同一个 Socket → 判定进入 RTSP-over-HTTP 隧道**

为什么隧道里数据要做 Base64 编解码?

原因：HTTP 传输安全承载**可见 ASCII 字符**，因为部分代理，老旧网关会对二进制字节直接丢弃数据包，不能直接传二进制字节流
混淆\r\n,阶段数据流，

1.Base64把二进制字节组成文本
2.通过`Content-Length`区分每个数据包边界；

原地操作，低拷贝数据：

利用数据在变换过程中"单调递减"特性，直接在原地缓冲区进行覆盖写入，省去额外内存和拷贝开销

| **RTSP over UDP** (标准模式)      | **TCP** (控制) + **UDP** (音频RTP + 视频RTP) | **100 ~ 300 毫秒** (极致低延迟) | **极差** (动态分配随机UDP端口，易被黑屏拦截) | **易花屏/马赛克/绿屏** (丢包不重传，但能保证绝对实时性) | 局域网监控、无人机/机器人图传、安防行业     |
| --------------------------------- | -------------------------------------------- | ------------------------------- | -------------------------------------------- | ------------------------------------------------------- | ------------------------------------------- |
| **RTSP over TCP** (交织模式)      | **纯 TCP** (复用 554 端口，数据交织)         | 1 ~ 2 秒                        | **强** (单通道传输)                          | **不丢包但会卡顿** (受 TCP 拥塞控制和重传影响)          | 跨公网远程监控查看、内网穿透拉流            |
| **RTSP-over-HTTP** (隧道伪装模式) | **HTTP / TCP** (伪装入 80/443 报文)          | 2 秒以上                        | **极强** (完全免杀所有网页防火墙)            | **不丢包但延迟最高** (多了一层 HTTP 封装开销)           | 极度严格的企业/学校防火墙环境下的视频流传输 |

##  RTSP和RTMP有什么区别

RTMP和RTSP定位不同。RTMP是Adobe的直播推流协议，基于TCP长连接，协议自带握手、连接、命令消息，适合从推流端到CDN/中转服务器的直播分发，生态成熟。RTSP是控制协议，常用于监控和NVR点播，可以跑在TCP或UDP上，RTP负责媒体传输，延迟可以更低，但分发和互联网直播生态不如RTMP。所以机器人监控推流用RTMP，是因为要推到局域网媒体节点再分发给客户端；如果要看超低延迟，可以考虑RTSP over UDP。

## 网络传输H.264文件头中：

```c++
┌─────────┬──────────────────────────┐
│NAL Header│        RBSP（载荷）       │
│  1 字节  │                          │
└─────────┴──────────────────────────┘
  0x65 → Type = 5 (IDR)
```

在服务器推流过程中，解析第一个字节后5位SPS，包含宽高信息，服务器需要，解码器不需要

```c++
  bool isFrame = (type == NAL_IDR || type == NAL_NONIDR);//是视频帧，i帧或P帧或B帧
```

H.264最基础的单元式NALU（网络抽象层单元），整个裸流就是一串连续的NALU连接而成，没有文件投，封装格式
1.前缀起始码，用来分割两个NALU，0x00 00 01  or  0x00 00 00 01
2.NALU头部1字节：F(1bit) + NRI(2bit) + NALU_Type(5bit)，看后五位NALU_Type

| Type 值 | 类型     | 说明                                         |
| ------- | -------- | -------------------------------------------- |
| 0x7     | SPS      | 序列参数集，分辨率、帧率、编码基础配置       |
| 0x8     | PPS      | 图像参数集，量化、熵编码等画面参数           |
| 0x5     | IDR I 帧 | 关键帧，可独立解码，不需要依赖前面任何帧     |
| 0x1     | P 帧     | 参考前面已解码帧，不能单独播放               |
| 0x2~0x4 | B 帧     | 双向参考前后帧，你开`max_b_frames=0`不会出现 |

关键规则：组 GOP 开头（每一个 I 帧之前）**必须先发送 SPS + PPS**，否则解码器无法解析画面。

3.NALU负载数据：头部之后剩余全部字节，就是真正的编码压缩图像数据
I 帧：本帧完整画面压缩信息
P 帧：相对于前一帧的差值压缩数据
SPS/PPS：配置信息，无画面像素数据

RTP包中，FU-A分包中还原NALU头部公式

```c++
原始NAL头1字节
= (FU_Indicator & 0xE0) | (FU_Header & 0x1F)
```

`FU_Indicator & 0xE0`：取出 **F+NRI 前 3 位**
FU_Header & 0x1F`：取出 **原始 NAL Type 后 5 位**
二者按位或，拼回完整 1 字节 NALU 头部
S bit (第 7 位)：1 = 分片**首片**
E bit (第 6 位)：1 = 分片**最后一片**
R bit (第 5 位)：保留，0

RTP 整包 = RTP 头部 + FU 分片负载 (FU_Indicator + FU_Header + NAL 分片裸数据)



## 重采样：

重采样本质上包含三个维度的转换：**采样率转换（Sample Rate Conversion）**、**声道布局转换（Channel Layout Mapping）** 和 **数据格式/位深转换（Sample Format Conversion）**。

\1. 音频解码后、送入播放器播放前（播放端适配）
\2. 音频数据送入编码器前（编码端适配）
\3. 混音（Mixer）与多路音频合成时
\4. 音频算法处理前（如 AEC 消除回声、NS 降噪、AGC 自动增益）

为什么需要？
消除硬件与软件参数不匹配造成的播放异常,. 统一内存数据布局（Packed vs Planar）
重采样库（如 FFmpeg 的 `swr_convert` 或 `libswresample`）可以方便地完成内存排列格式转换。



## 解复用：

流程：   

  调用 `avformat_open_input(&fmt_ctx, filename, NULL, NULL)` 打开多媒体文件或网络流（RTMP/RTSP）。
    调用 `avformat_find_stream_info(fmt_ctx, NULL)` 读取流信息，探测封装格式与各个 Stream 的元数据（编码格式、码率、分辨率等）。
     遍历 `fmt_ctx->streams` 或通过 `av_find_best_stream(fmt_ctx, AVMEDIA_TYPE_VIDEO, ...)` 分别找到音频流与视频流的索引位置。
    循环调用 `av_read_frame(fmt_ctx, &pkt)` 从容器中依次拉取一帧压缩数据 `AVPacket`。
   检查 `pkt.stream_index` 判断当前数据包属于音频还是视频，随后送入对应的解码器或转发处理。
  每次处理完毕调用 `av_packet_unref(&pkt)` 释放引用计数

总结：就是读文件，获取流信息，循环读包，送入解码器，核心av_read_frame

## 复用：

​    调用 `avformat_alloc_output_context2(&out_ctx, NULL, NULL, "out.mp4")`，FFmpeg 会根据文件后缀或显式指定的封装格式初始化复用器。
​    调用 `avformat_new_stream(out_ctx, NULL)` 为视频/音频分别创建输出 `AVStream`。
   通过 `avcodec_parameters_copy(out_stream->codecpar, in_codecpar)` 复制编码参数（如编码器 ID、宽高、采样率等）。
​     如果输出格式不含 `AVFMT_NOFILE` 标记，调用 `avio_open(&out_ctx->pb, "out.mp4", AVIO_FLAG_WRITE)` 打开输出文件
​     调用 `avformat_write_header(out_ctx, NULL)` 写入容器头部索引（如 MP4 的 moov/ftyp 初始结构）。
​    音视频流的基准时间戳（`time_base`）在输入和输出容器中通常不同，需调用 `av_packet_rescale_ts(&pkt, in_stream->time_base, out_stream->time_base)` 转换 `pts`、`dts` 和 `duration`
   调用 `av_interleaved_write_frame(out_ctx, &pkt)` 将 Packet 写入容器。该接口内部维护了一个按 DTS 时间戳排序的缓冲区，确保音视频数据包交错写入，避免播放时缓冲溢出
   数据写入完成后，调用 `av_write_trailer(out_ctx)` 写入文件索引尾部（如补全 MP4 的元数据索引）。

总结：创建输出上下文，写文件头，循环写包，时间基转换，写入文件尾

## AVPacket和AVFrame的数据结构

**`AVPacket`** 存储的是**压缩后**的媒体数据（如 H.264 编码的视频帧、AAC 编码的音频帧）
**`AVFrame`** 存储的是**解码后**的原始媒体数据（如 YUV/RGB 视频像素数据、PCM 音频采样数据）。

```c++
typedef struct AVFrame {
    uint8_t *data[AV_NUM_DATA_POINTERS]; // 各通道数据指针数组
    int linesize[AV_NUM_DATA_POINTERS];  // 各通道每行数据的字节跨度（Stride/Pitch，包含对齐填充）
    
    // 图像属性（视频帧有效）
    int width, height;                   // 图像宽高
    int format;                          // 像素格式 (AVPixelFormat，如 AV_PIX_FMT_YUV420P)
    int key_frame;                       // 是否为关键帧 (1 代表是，0 代表否)
    enum AVPictureType pict_type;        // 帧类型 (AV_PICTURE_TYPE_I, _P, _B)
    AVRational sample_aspect_ratio;      // 像素宽高比 (SAR)

    // 音频属性（音频帧有效）
    int nb_samples;                      // 单通道中的音频采样点数
    int sample_rate;                     // 采样率（如 44100, 48000）
    // FFmpeg 5.0+ 引入 AVChannelLayout 替代旧版 uint64_t channel_layout
    AVChannelLayout ch_layout;           // 声道布局（立体声、5.1声道等）

    // 时间与引用计数
    int64_t pts;                         // 显示时间戳（以解码器或滤镜的 time_base 为单位）
    int64_t pkt_dts;                     // 对应解码前 Packet 的 DTS
    AVBufferRef *buf[AV_NUM_DATA_POINTERS]; // 内存缓冲区引用计数结构
    // ...
} AVFrame;
```

​	pkt_dts的获取：解码器直接记录解码该帧对应的输入 `AVPacket` 的 DTS 值。主要用于调试、跟踪解码流水线延迟或滤镜处理。
   pts 的获取与纠正：
**理想情况：** 解码器内部维护了一个帧重排缓冲队列（处理 B 帧），当解码完成一帧并准备输出时，解码器会将该帧对应的原始 `AVPacket->pts` 赋给 `AVFrame->pts`。
**Packet PTS 缺失（`AV_NOPTS_VALUE`）情况：** 如果上游封包没有写入 PTS，解码器会尝试根据当前已解码的帧序号（Frame Number）和帧率（`framerate` / 采样率），推算出理论 PTS 填入 `AVFrame->pts`。

  

## 图形渲染管线流程：

CPU准备数据（VBO/VAO）,到顶点着色器（Vertex Shader）处理坐标，再到光栅化（Rasterization），最后到片段着色器（Fragment Shader）输出颜色。
（CPU 准备数据、顶点着色器、图元装配、光栅化、片段着色器到帧缓冲区的完整流程。）
**VBO**:顶点缓冲对象，分配再GPU显存的一块区域，存储海量顶点数据（如坐标、颜色、法线、UV 坐标等），用来VBO 允许我们在初始化时**一次性**将数据上传到显存，GPU 可以直接从本地显存高速读取，极大地提升了渲染效率。

**EBO**：去重，也叫IBO（Index Buffer Object），存储顶点索引值，为了**复用顶点数据，减少内存占用和传输带宽**。

**VAO**：**顶点数组对象**，记录“如何解析 VBO 和 EBO 数据的规则”

顶点着色器：决定“画在哪里”（MVP坐标转换）
片段着色器：决定“画成什么样”（颜色、光照）
它们之间通过 `out/in` 变量传递数据，而且光栅化阶段会对这些变量进行插值

## **CPU 和 GPU 是怎么交互数据的？**

现代 OpenGL 采用**异步命令队列（Command Queue）**机制。CPU 只负责通过 API（如 `glDrawArrays`）向 GPU 发送绘制指令和配置状态，然后立刻返回去执行下一行代码，不会阻塞等待。真正的海量数据（顶点、纹理坐标）是通过 **VBO（顶点缓冲对象）** 提前上传到显存（VRAM）中的，GPU 直接从本地显存读取数据，从而避免了 CPU 与 GPU 之间频繁的数据拷贝，最大化了带宽性能。

##  **什么是光栅化插值**

光栅化插值发生在 GPU 的**固定功能硬件（光栅化器）**中。当 GPU 将离散的 3D 顶点转化为连续的 2D 屏幕像素时，会根据像素在三角形内部的相对位置（**重心坐标 Barycentric Coordinates**），对顶点着色器输出的属性（如颜色、法线、UV坐标）进行**线性插值（Linear Interpolation）**。这保证了三角形内部的颜色和纹理能够平滑过渡。

##  **MVP 矩阵**：

MVP 是模型（Model）、视图（View）、投影（Projection）三个矩阵的复合。M 负责把物体从局部空间变换到世界空间；V 负责把世界空间变换到相机（观察）空间；P 负责把相机空间变换到裁剪空间（实现 3D 到 2D 的投影）
MVP 用于将模型局部坐标变换到裁剪空间。Model 矩阵处理物体自身的平移、旋转和缩放；View 矩阵表示相机的逆变换；Projection 矩阵负责透视或正交投影。顶点着色器中使用 `gl_Position = P * V * M * vec4(position, 1.0)`。由于使用列向量，矩阵从右向左生效。MVP 一般作为 uniform 每次绘制上传，而顶点坐标作为 attribute 从 VBO 中逐顶点读取。”

```c
int encode_video(StreamingContext *decoder, StreamingContext *encoder, AVFrame *input_frame) {
  if (input_frame) input_frame->pict_type = AV_PICTURE_TYPE_NONE;  // 让编码器自己决定帧类型

  AVPacket *output_packet = av_packet_alloc();   // 分配输出包

  int response = avcodec_send_frame(encoder->video_avcc, input_frame);  // ① 送帧

  while (response >= 0) {
    response = avcodec_receive_packet(encoder->video_avcc, output_packet);  // ② 收包
    if (response == AVERROR(EAGAIN) || response == AVERROR_EOF) {
      break;                                     // 编码器还要更多帧，或已结束
    }

    // ③ 设置包归属哪个流
    output_packet->stream_index = decoder->video_index;

    // ④ 计算 duration
    output_packet->duration = encoder->video_avs->time_base.den
                            / encoder->video_avs->time_base.num
                            / decoder->video_avs->avg_frame_rate.num
                            * decoder->video_avs->avg_frame_rate.den;

    // ⑤ 时间戳转换
    av_packet_rescale_ts(output_packet,
                         decoder->video_avs->time_base,
                         encoder->video_avs->time_base);

    // ⑥ 写入输出文件
    av_interleaved_write_frame(encoder->avfc, output_packet);
  }
  av_packet_unref(output_packet);
  av_packet_free(&output_packet);
  return 0;
}
```

## RTMP协议：

RTMP 协议本质上是一个“复合型协议”（也叫信令与媒体数据复用协议）。它在一个单独的 TCP 连接（默认 1935 端口）上，**同时兼顾了“控制信令（Control/Signaling）”与“媒体数据传输（Media Transport）”**。**实现了真正的**单连接、多路复用

![image-20260807144210163](C:\Users\95892\AppData\Roaming\Typora\typora-user-images\image-20260807144210163.png)

1.握手链接

RTMP 协议在建立连接时，客户端和服务器必须进行一个**复杂的三阶段握手**（包含 C0+C1、S0+S1+S2、C2 等数据包的交互）。这个类的核心作用就是作为一个**状态机**，负责解析接收到的握手数据，并生成对应的响应数据，直到握手成功。

客户端发送C0C1

服务端收到发送S0+S1+S2，S2就是C1，S1由三部分组成：4字节的时间戳，4字节的零占位符，随机数据

客户端端收到S0+S1+S2，进行检验包大小，然后将C2发送回服务端，就是S1


**消息（Messages）与块（Chunks）的拆装和解析**：
2.Chunk 分块传输阶段：先基本头再消息头

RTMP会把RtmpMessage切成Chunks块，所以Chunks类的作用在接收端，把网络缓冲区里交错而来的 Chunk 碎片缝合成完整的 `RtmpMessage`（`Parse`）；在发送端，把一个完整的 `RtmpMessage` 切碎成 Chunk 发送出去（`CreateChunk`）。

在RTMP协议中 **fmt** 在Basic Header最高两位，固定占2比特
决定 **Message Header（消息头）的长度与字段填充规则**
Fmt 的四种压缩格式:

| fmt 值 | Message Header 长度 | 规则说明                                                     |
| ------ | ------------------- | ------------------------------------------------------------ |
| 0      | 11 字节             | 全新消息首块，携带**完整绝对时间戳、消息长度、消息类型、MSID** |
| 1      | 7 字节              | 同流新消息，复用 MSID，只传时间戳增量、长度、类型            |
| 2      | 3 字节              | 同消息续块，复用长度、类型、MSID，只传时间戳增量             |
| 3      | 0 字节              | 完全复用前一块所有消息头信息，无 Message Header              |

**CSID**

Basic Header 除去 fmt 2bit 后的剩余位，长度可变：

- Basic Header 1 字节：CSID 占 6bit（范围 3~63）

- Basic Header 2 字节：CSID 占 14bit（64~319）第一个字节最后一位为0

- Basic Header 3 字节：CSID 占 22bit（64~65599）第一个字节最后一位位1

  //意思是 假如是2字节模式。 __000000 00000000代表有64是csid。

## 怎么处理半包，粘包问题？

登录服务器和信令服务器都通过“**包头长度字段 `len` + 接收缓冲区 `BufferReader`**”处理半包、粘包。

- 半包：收到的数据不足 4 字节包头，或不足 `head->len`，就不处理、不消费，数据留在缓冲区，等下次 `recv()` 拼完整。

- 粘包：完整处理一个包后调用 `buffer.Retrieve(head->len)`，再继续解析缓冲区后续数据。

- 登录服务器当前只处理一个完整包，粘在后面的包可能不能立刻处理。

- 信令服务器试图用 `while` 处理多个粘包，但半包时没有退出循环，存在空转占 CPU 的问题。
  可修改处理逻辑，处理逻辑改成

  ```c++
  enum class ParseResult {
      Consumed,  // 成功处理并消费一个完整包
      NeedMore,  // 半包，等待后续数据
      Invalid    // 非法包，断开连接
  };返回这些结果，Read函数进行校验，看是否需要继续循环读数据
  ```

一句话：**思路正确，都是长度字段拆包；但当前登录服务的粘包处理不完整，信令服务的半包处理存在死循环风险。**

在SrsTcpListener::listen()中实现了重点就是启动监听协程这个协程内部通常会运行一个死循环（`while(true) { st_accept(...) }`），专门负责等待新的 TCP 连接。一旦有连接进来，它就会唤醒并处理。这就是 SRS “单线程高并发”的秘密——用协程代替线程去“阻塞”等待连接。

在UDP路线中**`SrsUdpMuxListener::listen()`**实现多路复用，允许SRS在同一UDP端口上处理多种不同协议，根据包头特征把数据分发给不同处理器

```c++
    auto pc = std::make_shared<rtc::PeerConnection>(config);

    // 2. 创建数据通道
    auto dc = pc->createDataChannel("my-channel");
    dc->onOpen([]() {
        std::cout << "连接已建立！" << std::endl;
    });
    dc->onMessage([](auto data) {
        std::cout << "收到消息: " << std::get<std::string>(data) << std::endl;
    });

    // 3. 生成本地描述（Offer），发送给远端
    pc->onLocalDescription([&](rtc::Description description) {
        // 将这个 description 通过信令服务器发送给远端
        sendToRemoteViaSignaling(description);
    });

    // 4. 监听ICE候选，发送给远端
    pc->onLocalCandidate([&](rtc::Candidate candidate) {
        sendToRemoteViaSignaling(candidate);
    });

    // 5. 等待程序运行...
    std::cin.get();
    return 0;
}
```

## SFU架构和MCU架构：

| 架构    | 定义                                                         |
| ------- | ------------------------------------------------------------ |
| **SFU** | **选择性转发单元**：服务器只转发 RTP 包，**不解码、不混合**  |
| **MCU** | **多点控制单元**：服务器**解码→混合→重新编码**，输出一路合成流 |

MCU做混合的目的：**多路流变成一路流，从而降低带宽和客户端压力。**

SFU解析RTP/RTCP头部字段，是为了再不解码媒体负载**（Payload）\**的前提下，解决\**网络传输、帧完整性、时序对齐和多人路由**四大核心问题。



动态补轨：复用底层已建好的 DTLS/ICE 传输隧道，只在应用层与媒体层进行轨道级别的增量协商，实现**无感秒级拉起新画面/声音**。
复用PeerConnection这个对象（**底层的网络与安全连接容器**（维护着 ICE 打洞通道、DTLS 加密套件和 UDP 套接字），新增轨道，主要就是SDP协商过期，再次进行SDP协商

 



## NACK机制（RTX重传ARQ）:

完全解耦编码层级，主要活动在**RTP 会话/封装层与传输控制层**

​    fec，前向纠错，在每个数据包中添加一些关于前一个信息的信息，以防丢失。在接收端，需要重新构建它们，如果fec为5%，那么在丢包小于5%的情况下，都可以通过fec进行恢复，组成完整的帧，但是需要发送额外的包，会占用更大的带宽，具体实现不做讨论。
​    NACK机制，和TCP的ACK机制正好相反，NACK是用来确认丢包的发送协议，当接收方检测到有丢包时，它会发送NACK类型的RTCP包给发送方，发送方会重发这些数据。

## 同步编程，异步事件

   SRS服务器使用State-Threads 协程库，对于底层运行，当网络无数据时，ST 协程库拦截了 `read`，自动在 `epoll` 注册事件并调用 `yield` **主动让出 CPU 寄存器和栈帧**，让同一个物理线程内的其他协程去处理业务；待网络数据一到，`epoll` 唤醒并恢复上下文，协程无缝继续执行。这就是典型的“同步编程风格，异步事件性能”。

```

                    │      SRS 单物理主线程/事件循环     │
                    └──────────────┬────────────────┘
                                   │
                     1. 无就绪事件时，陷入阻塞等待
                                   ▼
                       epoll_wait(timeout)
                                   │
              ┌────────────────────┴────────────────────┐
              │ 2. 网卡收到数据 / 定时器到期 / 建立新连接    │
              ▼                                         ▼
   【就绪事件 A (Fd 12 可读)】               【就绪事件 B (Fd 18 可写)】
              │                                         │
              ▼                                         ▼
   找到 Fd 12 绑定的 协程 A                   找到 Fd 18 绑定的 协程 B
              │                                         │
 3. 上下文切换 (恢复寄存器 & 栈)              3. 上下文切换 (恢复寄存器 & 栈)
              ▼                                         ▼
   【协程 A 从 st_read 恢复】                 【协程 B 从 st_write 恢复】
              │                                         │
   处理完业务，无数据再度挂起                  处理完业务，缓冲区满再度挂起
```
